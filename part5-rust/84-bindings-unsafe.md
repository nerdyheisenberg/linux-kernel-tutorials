# Chapter 84 — Bindings, `unsafe`, and Writing Safety Contracts

> Sooner or later the abstraction you need does not exist and you must build it. This is the
> chapter about doing that responsibly: how `bindgen` works and where it fails, how to write
> a safety contract a reviewer can check, and how to decide whether your abstraction is
> actually sound. It is the most senior material in Part 5 — writing safe Rust is a skill;
> writing the *unsafe* code that makes safe Rust possible is a different and harder one.

---

## Theory & First Principles

### T.0 — Start here: three layers, and knowing which one you are in

Every kernel Rust file lives in exactly one of three layers, and **most confusion about Rust
in the kernel is someone reasoning about the wrong one.**

```
  LAYER 3   DRIVER CODE                              100% safe
            `let regs = pdev.io_request_and_map(0, ...)?;`
            No `unsafe`. Should read like ordinary Rust.
            -- if you are writing `unsafe` here, you are
               missing an abstraction. Go build it in layer 2.
  ---------------------------------------------------------------
  LAYER 2   ABSTRACTIONS (rust/kernel/)              unsafe INSIDE,
            pub fn io_request_and_map(...) -> Result<Devres<IoMem>> {
                // SAFETY: `res` is valid because ...              safe OUTSIDE
                let ptr = unsafe { bindings::ioremap(start, size) };
                ...
            }
            This is where the PROOFS live. Small, dense, reviewed hard.
  ---------------------------------------------------------------
  LAYER 1   BINDINGS (generated by bindgen)          100% unsafe
            pub unsafe fn ioremap(offset: u64, size: usize)
                -> *mut c_void;
            Machine-generated. No safety, no abstraction, no opinion.
            NEVER called directly from layer 3.
```

**The whole strategy of Rust-for-Linux is the shape of that pyramid:** unsafety is wide at the
bottom, narrow in the middle, and zero at the top, where the volume of code is greatest.
Invert it — let drivers call `bindings::` directly — and you have C with worse syntax.

**Now, what `unsafe` actually means**, because this is misunderstood constantly:

| What people think | What it is |
|---|---|
| "turns off the safety checks" | **no.** Borrow checking, lifetimes, and type checking all still apply. |
| "this code is dangerous" | **no.** It says: *I am making a promise the compiler cannot verify.* |

`unsafe` unlocks exactly five abilities: dereference a raw pointer, call an `unsafe` function,
implement an `unsafe` trait, access a `union` field or mutable `static`. **That is a closed
list**, which is precisely why the audit surface is bounded.

**The convention that makes this work is a two-sided contract**, and it is the discipline to
internalize:

```rust
/// # Safety
///
/// `ptr` must be a valid pointer to a live `struct device` whose
/// refcount the caller holds a reference of, and it must remain
/// valid for `'a`.
unsafe fn from_raw<'a>(ptr: *mut bindings::device) -> &'a Device { ... }
//  ^^^^^^ "# Safety" = the obligation I IMPOSE on my caller

// ... at the call site:
// SAFETY: `pdev.as_raw()` returns a live pointer; we hold a reference
// for the duration of probe(), so `'a` is satisfied.
let dev = unsafe { Device::from_raw(pdev.as_raw()) };
//  ^^^^^^ "SAFETY:" = the proof that I DISCHARGED the obligation
```

**`# Safety` states the obligation; `// SAFETY:` discharges it.** Both are mandatory in the
kernel tree (`clippy::undocumented_unsafe_blocks` is enabled). **This is what C has always
lacked — not the discipline, but the *fixed location* for it.** The same reasoning happens in
C review; it just happens in people's heads and in mailing-list threads, and is lost.

**And the honest ongoing problem, which you should be able to state:** `bindgen` regenerates
layer 1 automatically from C headers, but layer 2's *safety arguments* are hand-written
against the C code's *behaviour*. When a C function changes its locking rules or its
refcounting convention — which C maintainers are entirely free to do — **the bindings still
compile and the safety argument silently becomes false.** There is no mechanism that catches
this. It is the single most serious maintenance risk in the whole effort, and the reason
Rust abstractions have named maintainers who track their C counterparts.

**A practical rule to take away:** every `unsafe` block should be as small as possible and
immediately preceded by a `// SAFETY:` comment that a reviewer could *disagree with*. If the
comment is "SAFETY: this is fine," you have written nothing.

```bash
ls rust/bindings/ && head -40 rust/bindings/bindings_helper.h
grep -rn 'unsafe {' rust/kernel/ | wc -l
grep -rn '// SAFETY:' rust/kernel/ | wc -l    # these should be roughly equal
make LLVM=1 rustfmtcheck
```

### T.1 — The three layers, and which one you are writing

```
 ┌──────────────────────────────────────────────┐
 │ 3. Driver code                — 0 unsafe     │  you, usually
 ├──────────────────────────────────────────────┤
 │ 2. Abstraction (kernel crate) — some unsafe  │  you, this chapter
 ├──────────────────────────────────────────────┤
 │ 1. bindings                   — all unsafe   │  bindgen, automatic
 ├──────────────────────────────────────────────┤
 │ 0. C kernel                                  │
 └──────────────────────────────────────────────┘
```

The whole value of the arrangement depends on layer 2 being **correct**. A safe API over an
unsound abstraction is worse than raw `unsafe` everywhere, because it *looks* safe and
reviewers stop looking.

So the standard for layer-2 code is high:

> **Soundness rule.** An abstraction is *sound* if there is **no** way to cause undefined
> behaviour using only safe code, for *any* input, from *any* thread, in *any* order,
> including during unwinding and during `Drop`.

"No reasonable caller would do that" is not a soundness argument. The question is whether a
*malicious or careless* caller can, using only the safe API you exposed.

### T.2 — What `bindgen` does and where it fails

`bindgen` parses `rust/bindings/bindings_helper.h` with libclang and emits Rust declarations:

```c
/* C */
struct device { const char *init_name; struct device *parent; ... };
int device_register(struct device *dev);
```
```rust
/* Generated */
#[repr(C)]
pub struct device {
    pub init_name: *const core::ffi::c_char,
    pub parent: *mut device,
    ...
}
extern "C" {
    pub fn device_register(dev: *mut device) -> core::ffi::c_int;
}
```

**Everything bindgen produces is `unsafe` to call and carries no lifetime, nullability,
ownership, or thread-safety information.** It is a mechanical translation of syntax, not of
meaning.

What it cannot see at all:

| Invisible to bindgen | Why | Workaround |
|---|---|---|
| `static inline` functions | no symbol is emitted | a C shim in `rust/helpers/` |
| Function-like macros | textual, not typed | a C shim |
| `#define` constants with expressions | sometimes | a C shim or a `const` in Rust |
| Bitfields | layout is ABI-dependent | accessor shims |
| Variadic functions | no stable Rust ABI | wrapper with a fixed signature |
| `container_of` | a macro | implement in Rust with `offset_of!` |
| Anything not reachable from `bindings_helper.h` | not parsed | add the `#include` |

The shim pattern:

```c
/* rust/helpers/spinlock.c */
void rust_helper_spin_lock(spinlock_t *lock)
{
	spin_lock(lock);          /* the static inline, now with a symbol */
}
```

Adding a binding is therefore a two-step process: add the `#include` to
`bindings_helper.h`, and if the thing you need is a static inline or a macro, add a shim.
Reviewers will ask you to keep shims minimal and to name them `rust_helper_*`.

### T.3 — The five `unsafe` superpowers, and what each obliges you to prove

`unsafe` unlocks exactly five things. For each, the obligation:

| Ability | You must prove |
|---|---|
| **Deref a raw pointer** | It is non-null, aligned, points to an initialized value of the right type, is valid for the whole access, and no conflicting reference exists |
| **Call an `unsafe fn`** | Its documented `# Safety` preconditions hold |
| **Access a mutable `static`** | No data race; typically means a lock or single-threaded context |
| **`unsafe impl` a trait** | The trait's stated invariants hold — for `Send`/`Sync`, a concurrency argument |
| **Read a `union` field** | That field is the active one and its bit pattern is valid for its type |

Everything else — borrow checking, lifetimes, type checking, move semantics — still applies
inside an `unsafe` block. **`unsafe` widens what is expressible, it does not disable what is
checked.** Saying this correctly is a reliable interview differentiator.

### T.4 — The anatomy of a safety contract

Three documentation sections, and each has a precise job.

**`# Safety` on an `unsafe fn`** — states what the *caller* must guarantee:

```rust
/// Creates a reference to a `Device` from a raw pointer.
///
/// # Safety
///
/// * `ptr` must be non-null and point to a valid `struct device`.
/// * The caller must hold a reference (via `get_device`) that keeps the
///   device alive for the entire lifetime `'a`.
/// * No `&mut` reference to the same device may exist for `'a`.
pub unsafe fn from_raw<'a>(ptr: *mut bindings::device) -> &'a Device { ... }
```

Rules for writing one: be **specific** (name the function that establishes the precondition),
be **complete** (if you rely on it, state it), and be **checkable** (a reviewer should be able
to look at a call site and decide).

**`# Invariants` on a type** — states what is always true of a value of this type:

```rust
/// A registered misc device.
///
/// # Invariants
///
/// * `inner` always contains a `miscdevice` that has been successfully
///   registered with `misc_register` and not yet deregistered.
/// * The `name` pointer inside remains valid for the lifetime of `self`,
///   because it is owned by the `CString` field.
pub struct MiscDeviceRegistration<T> { ... }
```

Invariants are what let the `unsafe` blocks in the type's methods be short — each one can
say "by the type invariant, X" rather than re-proving it.

**`// SAFETY:` on an `unsafe` block** — discharges a specific obligation:

```rust
// SAFETY: `self.0` is a valid, registered miscdevice by the type
// invariant, and `misc_deregister` is called exactly once because
// `Drop` runs exactly once.
unsafe { bindings::misc_deregister(self.0.get()) };
```

**Bad safety comments, which you should reject in review:**

```rust
// SAFETY: this is safe                      <- says nothing
// SAFETY: ptr is valid                      <- why? who guarantees it?
// SAFETY: see above                         <- not checkable in isolation
// SAFETY: this should be fine               <- "should" is not a proof
```

A good one names the source of the guarantee. The test: **could a reviewer who has not read
the rest of the file verify this comment by looking at the type invariants and the function
signature?**

### T.5 — Designing a sound abstraction: the checklist

Work through these in order for every new abstraction.

**1. What does the C code guarantee, and what does it require?** This is usually
*undocumented*, and finding out is most of the work: read the implementation, read the
callers, read `Documentation/`, and — for anything load-bearing — **ask the maintainer on the
list**. A safety contract built on a guess is a liability.

**2. What are the lifetimes?** Who allocates, who frees, what keeps it alive, can it be freed
while Rust holds a pointer? Map this before writing any code.

**3. What is the thread-safety story?** Can the object be touched from two CPUs? From IRQ
context? Does it have its own internal lock? The answer determines `Send`/`Sync`, and an
`unsafe impl` with a hand-wave is the most common unsoundness in new abstractions.

**4. Can it move?** If C stores its address, it is `!Unpin` and you need `Opaque` +
`pin-init` (Ch. 80).

**5. What is the initialization state?** If C initializes it, use `MaybeUninit`/`Opaque`. If
Rust must initialize it in place, use `PinInit`.

**6. What is the error behaviour?** Which C returns are errors, are they errno or `ERR_PTR`
or NULL, and what state is the object in after a failure?

**7. Can a malicious safe caller break it?** Try to. Call methods in a strange order, call
them concurrently, drop things early, leak things (`mem::forget` is safe!), and pass
adversarial values.

**8. Is the API actually usable?** An abstraction so restrictive nobody can use it will be
bypassed with raw `bindings`, which is worse than no abstraction.

### T.6 — The leak footgun

```rust
core::mem::forget(value);   // SAFE. Does not run Drop.
```

Leaking is safe in Rust. Therefore **any abstraction whose soundness depends on `Drop`
running is unsound**, because a safe caller can always prevent it (`mem::forget`, an `Arc`
cycle, a `ManuallyDrop`).

Why this matters in the kernel: a common pattern is "register with C, and `Drop` unregisters."
If C keeps a pointer into a Rust object and the only thing preventing a dangling pointer is
`Drop`, a `mem::forget` gives C a pointer to freed memory.

The resolutions:
1. **Pin it in a box**, so the allocation outlives any forget of the handle (`Pin<KBox<T>>`
   forgotten leaks the box, which is safe — the memory is never freed).
2. **Make C's reference refcounted** (`Arc`), so C holds a count.
3. **Make the registration own the data** rather than borrowing it.

This is the same reasoning behind the standard library's `Pin` "Drop guarantee," and it is
the single most-missed issue in new kernel abstractions. Put it on your review checklist.

### T.7 — Aliasing, and why `&mut` is dangerous at the FFI boundary

Rust's `&mut T` is `noalias`. The optimizer relies on it: it may cache the value in a
register across a call, reorder loads and stores, and assume nothing else observes changes.

So this is **unsound**:

```rust
// WRONG: creates a &mut to memory C can also reach.
let dev: &mut bindings::device = unsafe { &mut *ptr };
unsafe { bindings::some_c_function(ptr) };   // C mutates it -> UB
```

The rule: **never create a `&`/`&mut` to memory that C may access concurrently.** Use
`Opaque<T>` (which is `UnsafeCell`, hence not `noalias`) and hand raw pointers to C.

This is why every C struct in the kernel crate is wrapped in `Opaque` rather than referenced
directly, and it is subtle enough that it is worth being able to explain — it is a favourite
question for anyone probing depth on Rust FFI.

### T.8 — Validity and the `AsBytes`/`FromBytes` traits

Rust types have **validity invariants**: `bool` must be 0 or 1, `char` must be a valid scalar
value, references must be non-null and aligned, enums must have a valid discriminant.
Producing an invalid value is instant UB, even if you never read it.

So reading device or user memory into a typed value requires proof:

```rust
/// # Safety
/// Implementers must ensure every bit pattern of the right size is a
/// valid value of this type.
pub unsafe trait FromBytes {}

/// # Safety
/// Implementers must ensure the type has no padding bytes, so that
/// reinterpreting it as bytes never exposes uninitialized memory.
pub unsafe trait AsBytes {}
```

Two distinct hazards:

- **`FromBytes` violated** → UB when a device writes 0x02 into what Rust thinks is a `bool`.
- **`AsBytes` violated** → an **information leak** (Ch. 102 §T.3): padding bytes are
  uninitialized kernel memory, and copying the struct to userspace or to a device exposes
  them. This is a real CVE class, which is why `CONFIG_GCC_PLUGIN_STRUCTLEAK` exists.

Check every `unsafe impl AsBytes` with `pahole`. If there is padding, the impl is wrong.

### T.9 — Verifying your work

`unsafe` code is not checked by the compiler, so you need other tools.

| Tool | Finds |
|---|---|
| **KASAN** | UAF, OOB, in the usual way |
| **KMSAN** | uninitialized memory use |
| **KCSAN** | data races, including ones your `unsafe impl Sync` claimed were impossible |
| **Miri** | UB in pure-Rust code — **cannot run kernel code**, but can run extracted logic |
| **`cargo +nightly miri`** on a userspace extraction | aliasing violations, invalid values |
| **Stacked/Tree Borrows** | the formal aliasing model Miri enforces |
| **`kunit`** | Rust unit tests in-kernel (`#[test]` via `rusttest`) |
| **`pahole`** | padding, for `AsBytes` |
| **Manual review** | everything else |

The practical discipline: **extract the pointer-manipulation logic into a form you can run
under Miri**, even if the kernel calls are stubbed. Miri catches aliasing mistakes that no
kernel-side tool will.

### T.10 — When to write an abstraction, and when not to

Judgement, which is the point of the chapter.

**Write one when:**
- Three or more call sites need it (the rule from `reference/system-design.md` §G4).
- The C contract is documented or you can get a maintainer to state it.
- The abstraction removes more `unsafe` than it adds.
- You can articulate the invariant in one sentence.

**Do not write one when:**
- You need it once. Use `unsafe` inline with a thorough `// SAFETY:` and move on.
- The C API's contract is genuinely unclear. An abstraction that encodes a *guess* is worse
  than none, because it launders uncertainty into apparent safety.
- The safe API you can build is so restrictive it is useless.
- The C API is being redesigned. Wait.

And the meta-answer: **the hardest part of a kernel Rust abstraction is not the Rust. It is
extracting an unwritten C contract from a subsystem and getting its maintainer to agree to
it.** That is a social and archaeological problem, and it is why abstractions land slowly.

### The `Opaque` + newtype pattern, in full

This is the canonical shape. Memorize it.

```rust
/// A `struct my_thing`.
///
/// # Invariants
///
/// The pointer wrapped by `self.0` is always valid and points to a
/// `struct my_thing` that has been initialized by `my_thing_init` and
/// not yet destroyed by `my_thing_destroy`.
#[repr(transparent)]
pub struct MyThing(Opaque<bindings::my_thing>);

impl MyThing {
    /// Borrows a `MyThing` from a raw pointer.
    ///
    /// # Safety
    ///
    /// * `ptr` must be non-null and point to a valid, initialized
    ///   `struct my_thing`.
    /// * The object must remain valid for the entire lifetime `'a`;
    ///   typically the caller holds a reference obtained from
    ///   `my_thing_get`.
    pub unsafe fn from_raw<'a>(ptr: *mut bindings::my_thing) -> &'a Self {
        // SAFETY: `MyThing` is `repr(transparent)` over `Opaque<my_thing>`
        // which is `repr(transparent)` over `my_thing`, so the cast is
        // layout-correct. Validity for `'a` is the caller's guarantee.
        unsafe { &*ptr.cast() }
    }

    pub fn as_raw(&self) -> *mut bindings::my_thing {
        self.0.get()
    }

    /// A safe operation: C documents `my_thing_read` as taking no locks
    /// and being callable from any context.
    pub fn read_value(&self) -> u32 {
        // SAFETY: by the type invariant, `as_raw()` is a valid, initialized
        // `my_thing`, which is all `my_thing_read` requires.
        unsafe { bindings::my_thing_read(self.as_raw()) }
    }

    /// A fallible operation.
    pub fn configure(&self, value: u32) -> Result {
        // SAFETY: as above; `my_thing_configure` accepts any u32 and
        // returns 0 or a negative errno.
        to_result(unsafe { bindings::my_thing_configure(self.as_raw(), value) })
    }
}

// SAFETY: `struct my_thing` is protected by its own internal spinlock
// (see drivers/my_subsystem/core.c, `thing->lock`), and all operations
// exposed above take that lock. Therefore it may be accessed from any
// thread.
unsafe impl Send for MyThing {}
// SAFETY: as above -- shared references only permit operations that take
// the internal lock.
unsafe impl Sync for MyThing {}
```

Six `unsafe` constructs, six justifications, each naming its source. **That density of
justification is the standard.**

### An owned wrapper with `Drop`

```rust
/// An owned `struct my_thing`, created and destroyed by us.
///
/// # Invariants
///
/// `self.0` always points to a `my_thing` created by `my_thing_create`
/// and not yet passed to `my_thing_destroy`.
pub struct OwnedThing(NonNull<bindings::my_thing>);

impl OwnedThing {
    pub fn new(config: u32) -> Result<Self> {
        // SAFETY: `my_thing_create` accepts any u32 and returns either a
        // valid pointer or an ERR_PTR.
        let ptr = from_err_ptr(unsafe { bindings::my_thing_create(config) })?;
        // INVARIANT: `from_err_ptr` rejected both null and ERR_PTR values,
        // so `ptr` is a valid, freshly-created `my_thing`.
        // SAFETY: as above.
        Ok(Self(unsafe { NonNull::new_unchecked(ptr) }))
    }
}

impl Drop for OwnedThing {
    fn drop(&mut self) {
        // SAFETY: by the type invariant this is a live `my_thing` created
        // by `my_thing_create`, and `Drop` runs at most once, so this is
        // the single matching `my_thing_destroy`.
        unsafe { bindings::my_thing_destroy(self.0.as_ptr()) };
    }
}
```

Now ask the §T.6 question: **does soundness depend on `Drop` running?** Here, no — a
`mem::forget` leaks the C object, which is a leak, not UB. Good. If instead C had stored a
pointer *into* a Rust-owned buffer, forgetting would be UB and the design would need fixing.

### Lab 84.2 — Build a complete abstraction from scratch

```rust
// SPDX-License-Identifier: GPL-2.0
//! A safe abstraction over `struct completion`.
//!
//! Chosen because it is small, the C contract is well-documented, and it
//! exercises pinning, lifetimes, and interruptible waiting.

use kernel::bindings;
use kernel::error::{to_result, Result};
use kernel::prelude::*;
use kernel::types::Opaque;
use core::marker::PhantomPinned;
use core::pin::Pin;

/// A completion: a one-shot (or counted) event that threads can wait for.
///
/// Wraps `struct completion`.
///
/// # Invariants
///
/// `self.inner` always contains a `struct completion` that has been
/// initialized by `init_completion` before any wait or complete operation
/// is performed on it. Initialization is guaranteed by `new()` being the
/// only constructor and by the type being `!Unpin`, so the object cannot
/// be moved after initialization.
#[pin_data]
pub struct Completion {
    #[pin]
    inner: Opaque<bindings::completion>,
    #[pin]
    _pin: PhantomPinned,
}

impl Completion {
    /// Creates a new, uncompleted `Completion`.
    pub fn new() -> impl PinInit<Self> {
        pin_init!(Self {
            inner <- Opaque::ffi_init(|slot: *mut bindings::completion| {
                // SAFETY: `slot` is valid, properly aligned, uninitialized
                // memory for a `struct completion`, per the `Opaque::ffi_init`
                // contract, which is exactly what `init_completion` requires.
                unsafe { bindings::init_completion(slot) };
            }),
            _pin: PhantomPinned,
        })
    }

    /// Signals the completion, waking one waiter.
    ///
    /// May be called from any context, including interrupt context.
    pub fn complete(&self) {
        // SAFETY: by the type invariant, `inner` is an initialized
        // `struct completion`. `complete()` is documented as safe from
        // any context and takes the completion's own internal lock.
        unsafe { bindings::complete(self.inner.get()) };
    }

    /// Signals the completion, waking all waiters.
    pub fn complete_all(&self) {
        // SAFETY: as `complete`.
        unsafe { bindings::complete_all(self.inner.get()) };
    }

    /// Waits for the completion, uninterruptibly.
    ///
    /// # Context
    ///
    /// May sleep. Must not be called from atomic context. (This is NOT
    /// enforced by the type system -- see Ch. 81 §T.10.)
    pub fn wait(&self) {
        // SAFETY: by the type invariant, `inner` is initialized.
        unsafe { bindings::wait_for_completion(self.inner.get()) };
    }

    /// Waits, returning `Err(ERESTARTSYS)` if a signal arrives.
    pub fn wait_interruptible(&self) -> Result {
        // SAFETY: by the type invariant, `inner` is initialized.
        // Returns 0 on success or -ERESTARTSYS if interrupted.
        to_result(unsafe {
            bindings::wait_for_completion_interruptible(self.inner.get())
        })
    }

    /// Waits with a timeout in jiffies.
    ///
    /// Returns `Ok(remaining_jiffies)`, where 0 means the wait timed out.
    pub fn wait_timeout(&self, timeout_jiffies: u64) -> Result<u64> {
        // SAFETY: by the type invariant, `inner` is initialized.
        // Returns 0 on timeout, or the remaining jiffies (>0) on success.
        let r = unsafe {
            bindings::wait_for_completion_timeout(
                self.inner.get(), timeout_jiffies as _)
        };
        Ok(r as u64)
    }

    /// Returns true if the completion has been signalled.
    pub fn is_done(&self) -> bool {
        // SAFETY: by the type invariant, `inner` is initialized.
        // `completion_done` takes the internal lock and is safe from any
        // context.
        unsafe { bindings::completion_done(self.inner.get()) }
    }
}

// SAFETY: `struct completion` contains a `wait_queue_head_t` with its own
// spinlock, and every operation above goes through a C function that takes
// that lock. Therefore a `Completion` may be moved between threads.
unsafe impl Send for Completion {}
// SAFETY: as above -- every `&self` method is internally synchronized, so
// sharing references across threads is sound.
unsafe impl Sync for Completion {}
```

Now **attack your own abstraction**, which is the actual exercise:

```rust
// Q1. Can a safe caller drop a Completion while a thread is waiting on it?
//     -> The waiter holds a `&Completion`, so the borrow checker prevents
//        dropping the owner while the reference lives... in SINGLE-THREADED
//        code. Across threads, the waiter must hold an Arc<Completion> or
//        a reference tied to something that outlives it.
//     -> CONCLUSION: this is sound only if callers are forced to use a
//        shared owner. Document it, or return a guard. THIS IS A REAL
//        FINDING and exactly the kind of thing review must catch.

// Q2. Can mem::forget cause UB?
//     -> Forgetting a Completion leaks it. C holds no pointer to it
//        (waiters hold pointers, but they are blocked ON it). Leak, not UB.
//        SOUND.

// Q3. Can it be moved after a waiter has queued?
//     -> !Unpin plus pin_init means it can only exist behind a Pin, so no.
//        SOUND. Remove the PhantomPinned and it becomes unsound -- try it.

// Q4. Is `wait()` in atomic context prevented?
//     -> No. Runtime `might_sleep()` only. Document with a `# Context`
//        section. NOT A SOUNDNESS BUG (it is a correctness bug the kernel
//        detects), but it must be documented.

// Q5. Double-complete?
//     -> C handles it: `complete()` increments a counter. SOUND.
```

Write the answers down. **That document — the attempted attacks and their outcomes — is what
you attach to the patch, and it is what a maintainer will actually read.**

### Lab 84.3 — Find the unsoundness

Each of these is a real mistake pattern. Identify the flaw before reading the answer.

```rust
// ---- A ----
pub struct Wrapper(*mut bindings::thing);
unsafe impl Send for Wrapper {}
unsafe impl Sync for Wrapper {}
// FLAW: no justification at all, and almost certainly false. `thing` may
// have no internal lock. An unsafe impl with no SAFETY comment is an
// automatic review rejection.

// ---- B ----
impl Wrapper {
    pub fn get(&self) -> &mut bindings::thing {
        unsafe { &mut *self.0 }
    }
}
// FLAW: hands out &mut from &self -- two callers can hold aliasing &mut.
// Also creates a noalias reference to memory C touches (§T.7).
// FIX: return a raw pointer, or use Opaque and expose typed operations.

// ---- C ----
pub struct Registration<'a> { data: &'a Data }
impl<'a> Registration<'a> {
    pub fn new(data: &'a Data) -> Result<Self> {
        unsafe { bindings::register(data as *const _ as *mut _) }?;
        Ok(Self { data })
    }
}
impl Drop for Registration<'_> {
    fn drop(&mut self) { unsafe { bindings::unregister(...) }; }
}
// FLAW: soundness depends on Drop running (§T.6). mem::forget(reg) leaves
// C holding a pointer to `data`, which may then be dropped -> UAF from
// SAFE code.
// FIX: take ownership (Arc<Data>), or require Pin<KBox<Registration>>.

// ---- D ----
#[repr(C)]
pub struct Header { version: u8, length: u32 }
unsafe impl AsBytes for Header {}
// FLAW: 3 bytes of padding between `version` and `length`. Copying this to
// userspace or a device exposes uninitialized kernel memory -- an info
// leak (Ch. 102 §T.3).
// FIX: #[repr(C, packed)], or reorder, or add explicit padding fields.
// VERIFY: pahole.

// ---- E ----
pub fn read_flag(&self) -> bool {
    unsafe { core::ptr::read(self.ptr as *const bool) }
}
// FLAW: the device or C may write any byte there. A `bool` that is not
// 0 or 1 is immediate UB, even before you use it.
// FIX: read a u8 and compare: `unsafe { read(p as *const u8) } != 0`.

// ---- F ----
pub fn callback_trampoline(data: *mut c_void) {
    let obj = unsafe { KBox::<Thing>::from_foreign(data) };
    obj.handle();
}
// FLAW: from_foreign takes ownership, so the Thing is DROPPED at the end
// of every callback. The second callback is a use-after-free.
// FIX: `borrow`, not `from_foreign` (Ch. 79 §T.7).
```

**Work through these until the flaws are obvious on sight.** They are, collectively, most of
what goes wrong in new kernel abstractions.

### Lab 84.4 — Verify with tooling

```bash
cd $KDIR

# 1. Sanitizers -- the same ones as for C.
./scripts/config --enable KASAN --enable KCSAN --enable UBSAN \
                 --enable RUST_DEBUG_ASSERTIONS --enable PROVE_LOCKING \
                 --enable DEBUG_ATOMIC_SLEEP
make LLVM=1 -j$(nproc)

# 2. Rust unit tests in-kernel.
./scripts/config --enable KUNIT --enable RUST_KERNEL_DOCTESTS
make LLVM=1 rusttest

# 3. Padding check for every AsBytes type.
pahole -C Header my_module.ko
pahole --show_private_classes my_module.ko | grep -B2 'padding'

# 4. Miri, on extracted logic. Kernel code cannot run under Miri, but the
#    pointer arithmetic can be extracted into a userspace crate.
cd /tmp && cargo new --lib miri_check && cd miri_check
# ... paste the pointer logic with C calls stubbed ...
rustup +nightly component add miri
cargo +nightly miri test
#    Miri enforces Stacked Borrows and catches aliasing violations that
#    KASAN cannot see.

# 5. Count and audit.
cd $KDIR
grep -rn 'unsafe' rust/kernel/my_subsystem.rs | wc -l
# Every one should have a SAFETY comment or be an `unsafe fn`/`unsafe impl`
# with a # Safety section:
grep -B1 'unsafe {' rust/kernel/my_subsystem.rs | grep -c 'SAFETY'
```

The two counts in step 5 should match. **Make that a CI check** — it is trivial to automate
and it catches the most common documentation lapse.

### Lab 84.5 — Review a real abstraction

```bash
cd $KDIR
# Pick one of these and review it as if it were being submitted to you.
$EDITOR rust/kernel/miscdevice.rs
$EDITOR rust/kernel/devres.rs
$EDITOR rust/kernel/irq.rs
```

For each, produce:

1. **The invariant list.** What is always true of a value of this type?
2. **The `unsafe` inventory.** For each block: what obligation, discharged how, by whom?
3. **The `Send`/`Sync` argument.** Is it stated? Is it *true*? Can you find a C path that
   violates it?
4. **The leak test.** Does soundness depend on `Drop` running? Try `mem::forget`.
5. **The adversarial test.** Call the safe API in a hostile order. Does anything break?
6. **The usability test.** Write a 20-line driver against it. Is it pleasant?

Write up one of these as a mailing-list review. **That artifact is directly what a kernel Rust
maintainer does, and having written one is a strong thing to be able to say.**

### Lab 84.6 — Extract an undocumented C contract

Pick a C API with no Rust abstraction and no clear documentation. Then:

```bash
# 1. Read the implementation.
$EDITOR drivers/foo/core.c

# 2. Read every caller -- the real contract is what callers assume.
grep -rn 'foo_register\|foo_unregister' --include='*.c' . | head -30

# 3. Look for the locking rules.
grep -B5 -A5 'foo_register' drivers/foo/core.c | grep -i 'lock\|mutex\|spin'

# 4. Check what contexts it is called from.
#    Add a might_sleep() or a WARN_ON(in_interrupt()) and run.

# 5. Check git history for fixes -- bugs reveal the contract.
git log --oneline -- drivers/foo/core.c | head -30
git log -S'foo_register' --oneline | head

# 6. Check the mailing list.
b4 search 'foo_register'
```

Then write the contract as you understand it, in the `# Safety` form, and **send it to the
maintainer as a question**, not as a patch: *"I am writing a Rust abstraction for this. Is
the following an accurate statement of the contract?"*

**This is the actual bottleneck in kernel Rust work**, and being comfortable with it is the
difference between someone who can write Rust and someone who can add Rust to Linux.

## 4. Further reading

**Essential**
- ***The Rustonomicon*** — free online. **Read it completely before writing any abstraction.**
  Particularly: "Meet Safe and Unsafe," "Data Layout," "Ownership," "Subtyping," "Type
  Conversions," "Uninitialized Memory," "Unwinding," "Concurrency," and "Implementing Vec"
  (which is the single best worked example of building a safe abstraction over `unsafe`)
- `Documentation/rust/coding-guidelines.rst` — the kernel's documentation standard
- The `unsafe-code-guidelines` repository (rust-lang) — the working notes on what is and is
  not UB. Not normative, but the best available account

**Models and formalism**
- Stacked Borrows: Jung et al., "Stacked Borrows: An Aliasing Model for Rust," *POPL*, 2020
- Tree Borrows (the successor model) — Villani's work and the Miri implementation
- Jung et al., "RustBelt: Securing the Foundations of the Rust Programming Language,"
  *POPL*, 2018 — the proof that `unsafe`-implemented libraries can be sound
- Astrauskas et al., "How Do Programmers Use Unsafe Rust?," *OOPSLA*, 2020 — empirical data
  on real `unsafe` usage patterns and their failure modes

**Tools**
- **Miri** — `cargo +nightly miri test`. The single most valuable tool for `unsafe` code
- `pahole` — padding, for `AsBytes`
- KASAN, KCSAN, KMSAN, UBSAN — the kernel-side detectors
- `cargo-careful`, `cargo-geiger` (userspace, but the ideas transfer)
- `bindgen` documentation — the flags, the blocklists, and the `--wrap-static-fns` option

**Code to read as exemplars**
- `rust/kernel/types.rs` — `Opaque`, `ForeignOwnable`; short and dense
- `rust/kernel/sync/arc.rs` — a complete, carefully-documented abstraction
- `rust/kernel/devres.rs` — the hardest lifetime problem in the crate, solved
- The `zerocopy` crate — the best userspace treatment of `AsBytes`/`FromBytes`, with
  derive macros that *prove* the absence of padding
- The `pin-project` and `pin-init` crates — `Pin` done properly

**Discussion**
- LKML threads on any new Rust abstraction — the review comments are the best available
  training material
- Kangrejos talks, particularly on safety-contract methodology
- "Unsafe Rust is harder than C" (a recurring blog-post genre) — read a couple; the thesis is
  that `unsafe` Rust has *more* rules than C, not fewer, and it is correct
