# Chapter 57 — ext4 internals

> **Goal:** Understand the filesystem that most Linux systems actually run on, not as a list of features but as a thirty-year sequence of compatible decisions. Understand block groups and flex_bg, extents and the extent tree, htree directories, the multi-block and mballoc allocators, delayed allocation and its consequences, the inode table's fixed-size problem, metadata checksums, and the `data=ordered` guarantee that shaped a generation of application code. By the end you can read `fs/ext4/`, use `debugfs` and `dumpe2fs` fluently, diagnose ext4 performance and corruption problems, and explain precisely which of ext4's properties are design and which are historical accident.

## Theory & First Principles

### T.0 — Start here: a filesystem that can never break its own past

```bash
# Mount a filesystem made in 1993 with a 2025 kernel:
mount -t ext4 /dev/sdb1 /mnt      # an ext2 image. It just works.
dumpe2fs -h /dev/sdb1 | grep features
```

**ext4 is the same code path as ext2 and ext3.** One driver, three filesystems, thirty years.
That constraint — not a design vision — explains nearly every structural choice in ext4.

**Watch the constraint operate.** ext2 stored a file's blocks as direct and indirect pointers:

```
  inode: 12 direct pointers  ->  blocks 0..11
         1 single-indirect   ->  a block of 1024 pointers
         1 double-indirect   ->  1024 * 1024 pointers
         1 triple-indirect   ->  1024^3 pointers
```

For a **contiguous 1 GiB file** that is 262,144 pointers, requiring ~256 indirect-block reads
just to know where the data is — to express a fact that fits in eight bytes ("starts at X,
runs for 262,144 blocks").

Extents fix it:

```c
struct ext4_extent {
	__le32 ee_block;     /* first file block this covers   */
	__le16 ee_len;       /* how many blocks (up to 32768)  */
	__le16 ee_start_hi;  /* physical block, 48 bits total  */
	__le32 ee_start_lo;
};   /* 12 bytes describes up to 128 MiB */
```

**But where do the extents go?** In the same 60 bytes `i_block[]` that held the old pointers —
reinterpreted, gated by an `EXT4_EXTENTS_FL` inode flag, with the old format still fully
supported. **The on-disk inode did not grow and old filesystems still mount.** That is the
whole ext4 story in one structure.

**The feature-flag mechanism is the general lesson**, and it is a genuinely good piece of
engineering worth stealing:

| Flag set | Meaning | An old kernel will... |
|---|---|---|
| `COMPAT` | new feature, harmless | mount read-write safely |
| `RO_COMPAT` | reading is safe, writing would corrupt | mount **read-only** |
| `INCOMPAT` | the format changed fundamentally | **refuse to mount** |

Three categories, checked at mount time, and they make a 30-year format evolution
*mechanically safe*: a kernel that does not understand a feature cannot silently corrupt the
filesystem. Compare Ch. 24 §T.0 on syscall extensibility — same problem, same shape of answer:
**encode your compatibility contract in the data, and check it before acting.**

**Three ext4 ideas worth carrying forward:**

1. **Delayed allocation.** Do not decide where a block goes when `write()` happens; decide at
   writeback, when you know the *total* size and can pick one contiguous run. This is
   `IOMAP_DELALLOC` from Ch. 55 §T.0. It is also why `ENOSPC` can be reported at `close()`.
2. **Block groups.** The device is split into groups, each with its own bitmaps and inode
   table, and a file's data is placed near its inode. Designed to minimise seeks — and on
   NVMe, now nearly pointless (Ch. 51 §T.0).
3. **`data=ordered` as the default.** Write data before committing the metadata that points
   at it. Slower than `writeback`, but it makes "file contains someone else's deleted data
   after a crash" impossible. Ch. 61 §T.4.

**And the honest assessment**, which is why Ch. 58 and 59 exist: ext4 is the conservative
choice — mature, predictable, fsck-able, well-understood failure modes — and it is
structurally limited by compatibility. It has no data checksums, no snapshots, a single
allocation group lock heritage that limits parallelism, and an `fsck` time proportional to
filesystem size. XFS and btrfs each abandoned compatibility to escape one of those limits.

```bash
dumpe2fs -h /dev/sda1                 # features, journal, group count
filefrag -v /large/file               # extents, and fragmentation
debugfs -R 'stat <12>' /dev/sda1      # a raw inode
cat /proc/fs/jbd2/sda1-8/info         # journal commit statistics
```

### T.1 ext4 is a compatibility story, not a design

Almost every peculiarity in ext4 follows from one constraint: **it had to be able to mount ext2 and ext3 filesystems, and — for a long time — ext3 had to be able to mount ext4 ones.**

The lineage:

| Year | Filesystem | The problem it solved | The cost |
|---|---|---|---|
| 1992 | ext | first real Linux fs | no timestamps, 2 GB max, terrible |
| 1993 | ext2 | FFS-style block groups, fast | `fsck` after every crash |
| 2001 | ext3 | **journal** (Ch. 61) — bounded recovery | write amplification |
| 2006 | ext4 | extents, >16 TiB, delalloc, faster fsck | format divergence |

Each step is additive, gated by the three feature-flag sets (Ch. 56 §T.3(d)). This is why a modern `mke2fs` can still produce something a 1995 kernel would mount, and why `fs/ext4/` contains code for block-mapped *and* extent-mapped files, linear *and* hashed directories, 128-byte *and* 256-byte inodes.

The intellectually honest summary: **ext4 is an excellent engineering achievement and a mediocre design.** It is fast, extraordinarily well-tested, and its on-disk format is constrained by decisions made when 1 GB was a large disk. XFS and btrfs (Ch. 58, 59) are better *designs*; ext4 is the one with 30 years of `e2fsck` hardening behind it. Both facts matter.

The lesson for Ch. 56 §T.3: the feature-flag mechanism *worked*. A format designed in 1993 evolved through three major revisions without ever breaking an existing image. Few software artefacts achieve that.

### T.2 Block groups: locality as the primary mechanism

Ext2 inherited McKusick's FFS insight: on a rotating disk, **the dominant cost is seeking, so put related things near each other.** Divide the device into *block groups*, each self-contained:

```
┌──────────┬──────────┬──────────┬──────────┬──────────┬───────────────┐
│ Super    │ Group    │ Block    │ Inode    │ Inode    │ Data blocks   │
│ block    │ descrs   │ bitmap   │ bitmap   │ table    │               │
│ (copy)   │ (copy)   │ 1 block  │ 1 block  │ n blocks │               │
└──────────┴──────────┴──────────┴──────────┴──────────┴───────────────┘
```

One block bitmap block describes 8 × 4096 = 32768 blocks = **128 MiB**. That is the group size, and it is a direct consequence of the bitmap fitting in one block — an arbitrary-looking number that falls straight out of the format.

The allocation policies:

- A new **directory** goes in a group with above-average free space and inodes (spread directories out).
- A new **file** goes in its parent directory's group (keep a directory's files together).
- A file's **data** goes in the same group as its inode.
- Subsequent blocks go near the previous ones (goal blocks — Ch. 56 §T.7).

This is a genuinely good design that survives on SSDs for a different reason: contiguity still matters because it produces larger I/Os and fewer metadata lookups, even without seek costs.

**`flex_bg`** (ext4) relaxes the layout: group the bitmaps and inode tables of 16 consecutive block groups together, leaving large contiguous data regions. The metadata for 2 GiB of filesystem lands in one place instead of being scattered every 128 MiB. Benefits: large contiguous allocations become possible, `e2fsck` reads metadata sequentially, and metadata writes cluster.

**`meta_bg`** and **`sparse_super`** address a different problem: the *group descriptor table* is replicated in every group, and at large sizes this dominates. A 100 TiB filesystem has ~800,000 groups; 64 bytes per descriptor is 50 MiB of descriptors, replicated. `sparse_super` replicates only in groups 0, 1, and powers of 3, 5, 7. `meta_bg` splits the descriptor table so each group has only its own metadata group's descriptors.

Follow the chain: bitmap size → group size → descriptor table size → `sparse_super` → `meta_bg`. **Each fix addresses a scaling limit created by the previous design, without changing it.** That is what compatibility-constrained evolution looks like.

### T.3 Extents: the single biggest ext4 improvement

Ext2/ext3 mapped file blocks with **direct and indirect blocks**:

```
inode->i_block[0..11]  -> 12 direct block numbers
inode->i_block[12]     -> single indirect: 1024 block numbers
inode->i_block[13]     -> double indirect: 1024 × 1024
inode->i_block[14]     -> triple indirect: 1024 × 1024 × 1024
```

Costs, for a 1 GiB file with 4 KiB blocks:

| | Indirect blocks | Extents |
|---|---|---|
| Metadata blocks needed | **257** (1 single + 256 double-indirect leaves… ) | **1** (if contiguous) |
| Block-map reads for a random offset | up to 3 | 1 (in-inode) |
| Deleting the file | read + free 257 metadata blocks | free 1 extent |
| Bytes of metadata | ~1 MiB | 12 bytes |

The worst case is deletion: `rm` of a large file on ext3 was famously slow because freeing required walking the entire indirect tree. Extents make it O(extents).

The extent format:

```c
/* Every extent-mapped inode's i_block[] starts with this. */
struct ext4_extent_header {
	__le16	eh_magic;	/* 0xF30A */
	__le16	eh_entries;	/* entries in use */
	__le16	eh_max;		/* capacity */
	__le16	eh_depth;	/* 0 = leaf (extents), >0 = index */
	__le32	eh_generation;
};

struct ext4_extent {		/* leaf: an actual mapping */
	__le32	ee_block;	/* first file block */
	__le16	ee_len;		/* length; >32768 means UNWRITTEN */
	__le16	ee_start_hi;	/* high 16 bits of the physical block */
	__le32	ee_start_lo;
};

struct ext4_extent_idx {	/* internal: a pointer to a child node */
	__le32	ei_block;	/* covers file blocks >= this */
	__le32	ei_leaf_lo;
	__le16	ei_leaf_hi;
	__u16	ei_unused;
};
```

Three design points worth noting:

**(a) `i_block[]` is reused.** 60 bytes holds a header plus 4 extents. A file with ≤ 4 extents needs **no external metadata at all** — the entire block map is in the inode. Most files qualify. This is the same inline-small-case optimisation as Ch. 54 §T.7(c).

**(b) `ee_len > 32768` encodes "unwritten".** Ch. 55 §T.8's unwritten extents, stolen from the high bit of the length. Hence the maximum extent length is 32768 blocks = **128 MiB**, which is why `filefrag` on a large contiguous file shows many 128 MiB extents rather than one — they are physically contiguous but format-limited.

**(c) It is a B+tree, not a list.** `eh_depth > 0` means index nodes. The tree is searched by file block number. For a heavily fragmented file the tree grows, and the *metadata* becomes the cost — which is why fragmentation hurts twice.

The extent tree is **not** a general B+tree: it is only indexed by file offset, never by physical block. That is why ext4 cannot cheaply answer "which file owns physical block N?" — `e2fsck` must build that map by full scan, and it is why ext4 has no reflink (see §T.9).

### T.4 htree: hashed directories without breaking `readdir`

Ext2 directories are linear (Ch. 56 §T.6(b)). Creating n files is O(n²). With n = 100,000 this is minutes.

Ext3 added **htree**: a hash index over the directory. The constraint that shaped it:

> The index must be **invisible to a reader that does not understand it.**

Because `dir_index` is a `COMPAT` feature — an old kernel must still be able to read the directory correctly. So the index cannot be a separate structure; it must hide inside the directory data in a way that a linear reader skips.

The trick: the index nodes are stored in the directory's data blocks, **disguised as a single directory entry with `rec_len` spanning the whole block and `inode == 0`**. A linear reader sees one deleted entry covering the block and skips it. An htree-aware reader recognises the fake `.`/`..` structure and uses the index.

```
Block 0:  "." ".." <fake entry covering the rest> + dx_root
             ├── hash_version, indirect_levels, limit, count
             └── dx_entry[]: { hash, block }
Block 1..n: ordinary directory entry blocks, sorted by hash
```

The hashing:

- Hash the name (half-MD4 by default, or TEA, or legacy).
- **The low bit is reserved as a collision flag.** Two names with the same hash must land in the same leaf and be found by a sequential scan of colliding entries; the flag says "continue into the next block."
- The hash is **seeded per filesystem** (`s_hash_seed`) so an attacker cannot craft names that all collide — a deliberate defence against algorithmic complexity attacks.

And the hard part: **`readdir` offsets.** POSIX requires `telldir`/`seekdir` cookies to remain valid. A linear directory uses the byte offset. An htree directory must use the *hash* as the cookie, because entries move between blocks on split. So `readdir` on an htree directory returns entries in **hash order**, not creation order or any order the user can predict.

This has a real consequence: **`readdir` order on ext4 is effectively random with respect to inode number**, so `tar`ing or `rsync`ing a large directory reads inodes in random order, which is slow. That is why `e2fsck -D` (optimise directories) and tools that sort by inode before stat-ing exist. It is also the origin of the folklore "always sort `readdir` output by inode before stat-ing" — measurable, and worth several times' speedup on rotating media.

The 3-level htree limit caps a directory at roughly 10–15 million entries. `large_dir` (4.13+) adds a level.

### T.5 mballoc: allocation as a two-level problem

The multi-block allocator answers "give me n contiguous blocks near goal g" with a structure borrowed from memory allocators.

**Buddy bitmaps.** For each block group, ext4 maintains in memory a buddy structure: bitmaps of free runs of size 1, 2, 4, 8, … 8192 blocks. Finding the smallest free run ≥ n is then a scan of one bitmap, not of the whole group. This is Ch. 22's buddy allocator applied to disk blocks — the same problem (allocate power-of-two contiguous runs, minimise fragmentation), the same solution.

**Two preallocation spaces**, solving two different problems:

| | Inode PA | Locality-group PA |
|---|---|---|
| Owned by | one file | one CPU |
| For | large files | **small files** |
| Size | grows with the file | `s_mb_group_prealloc` (512 blocks) |
| Purpose | keep one file contiguous | keep *concurrently created small files* from interleaving |

The locality-group PA is the clever one. Four processes each writing many small files would, with per-file allocation, interleave their blocks. Instead each *CPU* gets a preallocation window, so files created on the same CPU cluster together. It trades a little space for a lot of locality, and it is why `tar -x` on ext4 produces reasonably laid-out files.

**Stream detection**: files above `s_mb_stream_request` (16 blocks) bypass the locality group and get their own inode PA, because large files should not share a window with small ones.

Tunables under `/sys/fs/ext4/<dev>/`:

```
mb_stats            enable statistics (then read /proc/fs/ext4/<dev>/mb_groups)
mb_max_to_scan      how hard to look for a best fit
mb_min_to_scan      minimum scan before accepting
mb_order2_req       use order-2 (buddy) allocation above this size
mb_stream_req       stream threshold
mb_group_prealloc   locality-group window size
```

These are a rare case where the allocator's policy is directly observable and tunable, which makes Lab 57.5 possible.

### T.6 Delayed allocation and the `data=ordered` story

Ch. 55 §T.8 covered delayed allocation generally. Ext4's version had a *social* consequence worth studying.

**Ext3's `data=ordered`** (the default) guaranteed: data blocks are written to disk **before** the metadata that references them is committed. The motivation was security — without it, a crash could leave an inode pointing at blocks containing someone else's old data. But it had a side effect: because the journal commits every 5 seconds and flushes all pending data first, ext3 in `data=ordered` mode provided something close to "all writes are durable within 5 seconds, in order."

Applications came to depend on this. The canonical pattern:

```c
	fd = open("file.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
	write(fd, data, len);
	close(fd);
	rename("file.tmp", "file");       /* NO fsync */
```

On ext3 this was *usually* safe. On ext4 with delayed allocation, the rename's metadata could be journalled and committed while the data was still only in the page cache — a crash then left a **zero-length file**. In 2009 this hit Ubuntu users hard: after a crash, configuration files across the desktop were empty.

The resolution is the interesting part. Ted Ts'o's position was technically correct: the applications were buggy; POSIX never promised this; `fsync` is required. The counter-argument was Hyrum's Law (Ch. 24 §T.1): thousands of applications depended on the observable behaviour, so changing it broke them regardless of what the specification said.

The compromise, still in ext4 today:

```c
	/* In ext4_rename and ext4_unlink paths: if the target had
	 * delayed-allocated data, force it out before the rename. */
	if (ext4_should_dioread_nolock(inode) || dirty_pages_pending)
		ext4_alloc_da_blocks(old_inode);
```

Plus `auto_da_alloc` (on by default): on `rename()`-over-existing and on `truncate`-then-`close`, flush the delayed allocation. This is **a heuristic implementing an unspecified guarantee that applications rely on**.

Three lessons:

1. **Observable behaviour becomes contract.** (Ch. 24 §T.1 — this is the storage stack's canonical example.)
2. **The right answer was still to use `fsync`,** and the episode taught a generation of application developers to do so. `sqlite`, `git`, and every serious database do.
3. **`data=ordered` is an ext3/ext4 property, not a POSIX one.** Code relying on it is unportable to XFS, btrfs, or any network filesystem.

The mode table, for completeness:

| Mode | Journals | Crash guarantee | Speed |
|---|---|---|---|
| `data=journal` | metadata **and data** | strongest: no stale data, data is atomic with metadata | slowest (double writes) |
| `data=ordered` | metadata; **data written first** | no stale data exposure | default |
| `data=writeback` | metadata only | **stale data can be exposed** after a crash | fastest |

`data=writeback` is genuinely dangerous on a multi-user system: a crash can expose another user's deleted file contents in your newly-extended file. It is a legitimate choice only when nothing sensitive is on the filesystem.

### T.7 The fixed inode table, and the cost of getting it wrong

`mke2fs` fixes the inode count at format time (`-i bytes-per-inode` or `-N count`). It cannot be changed afterwards — `resize2fs` can grow the filesystem but the inode-per-group count is in the superblock and the tables are positionally addressed (Ch. 56 §T.4).

The failure mode: `ENOSPC` with `df` showing free space. `df -i` shows the truth. This bites mail spools, build trees, and container image stores — anything with many small files. The default of one inode per 16 KiB is wrong for both extremes.

Inode *size* is separately configurable (128 bytes for ext2 compat, 256 default). The extra 128 bytes hold:

- **Nanosecond timestamps** plus the extra epoch bits that push the 2038 limit to 2446. **A 128-byte-inode ext4 filesystem is 2038-limited and cannot be fixed.**
- `i_crtime` — creation time, exposed via `statx(STATX_BTIME)`.
- **Inline extended attributes** — small xattrs stored in the inode itself, avoiding a separate block. SELinux contexts fit here, which matters enormously: without it, every file on a SELinux system needs an extra block read.
- **Inline data** (`inline_data` feature): files smaller than the free inode space are stored *in the inode*. No data block at all.

`i_extra_isize` records how much of the extra space is used, allowing further growth. A rare case of successful in-place format extension.

### T.8 Metadata checksums: retrofitting integrity

`metadata_csum` (3.6+) adds CRC32c to the superblock, group descriptors, bitmaps, inodes, extent blocks, directory blocks, and the journal.

What it buys: **detection** of silent corruption in metadata, and — crucially — protection against `e2fsck` "repairing" a filesystem based on corrupt data and making things worse.

What it does **not** buy: data checksums. **Ext4 does not checksum file data, at all.** Silent bit rot in your files is undetectable by ext4. This is the single largest functional gap versus btrfs and ZFS, and it is why those filesystems exist. If data integrity matters, ext4 alone is insufficient; you need dm-integrity beneath it, or a different filesystem.

The retrofit was hard, and the difficulty is instructive:

- Each checksum needs a **seed** so that a block moved elsewhere fails validation. Ext4 uses the filesystem UUID plus the inode number plus the generation. Without the position in the seed, an attacker (or a misdirected write) could relocate a valid block.
- Group descriptors grew from 32 to 64 bytes, requiring an `INCOMPAT` flag.
- The journal needed its own checksum scheme (`journal_checksum`), because a torn journal write must be detected — otherwise replay makes corruption worse.
- Directory blocks had no spare space, so the checksum hides in a **fake directory entry at the end of the block** with `inode == 0` and `rec_len == 12` — the same disguise trick as htree (§T.4).

That last one is a lovely illustration of format-compatibility engineering: *when you have no room, hide the new field where an old reader will ignore it.*

### T.9 What ext4 cannot do, and why

An honest list, with the format reason for each:

| Missing | Why the format prevents it |
|---|---|
| **Data checksums** | no per-block metadata space for file data; would need a new tree |
| **Snapshots** | no CoW; blocks are updated in place |
| **Reflink / `copy_file_range` acceleration** | no reverse map, so a shared block cannot be freed correctly; no refcount tree |
| **Shrink while mounted** | must relocate data with no atomic mechanism |
| **Online `fsck`** | no consistent snapshot to check against |
| **>1 EiB** | 48-bit block numbers |
| **Inode count change** | positional inode numbers (Ch. 56 §T.4) |
| **Compression** | no per-extent compressed-length field |

Each entry is a consequence of a decision that was correct in 1993. Btrfs and XFS have most of these because they were designed later with different constraints — XFS added reflink by having a reverse-map B+tree and a refcount B+tree, structures ext4 has no room for.

The counter-argument, which is strong: ext4 is **the most tested filesystem in existence**, `e2fsck` can repair damage that would destroy a btrfs filesystem, and its performance is predictable. "Boring and reliable" is a legitimate design goal. For a database server with a UPS and good backups, ext4 remains a defensible choice in 2026.

### T.10 The features you should actually know

```sh
dumpe2fs -h /dev/sda1 | grep -i 'features'
```

| Feature | Meaning | Default? |
|---|---|---|
| `has_journal` | ext3+ journalling | yes |
| `extent` | §T.3 | yes |
| `dir_index` | §T.4 htree | yes |
| `flex_bg` | §T.2 metadata clustering | yes |
| `64bit` | 64-bit block numbers, >16 TiB | yes (modern) |
| `metadata_csum` | §T.8 | yes (modern) |
| `metadata_csum_seed` | UUID change without rewriting all checksums | no |
| `inline_data` | §T.7 small files in the inode | no |
| `large_dir` | 4-level htree | no |
| `sparse_super`/`sparse_super2` | §T.2 fewer superblock copies | yes/no |
| `uninit_bg`/`bigalloc` | skip unused inode table on fsck / cluster allocation | varies |

`fast_commit` deserves a note: it adds a second, finer-grained journal area recording *logical* operations ("file X was extended to size S") rather than physical blocks, so an `fsync` need not write a full transaction. It roughly halves fsync latency on some workloads. It is the most significant recent ext4 change and a good example of Ch. 61's ideas applied incrementally.

### 1.2 The superblock, abridged

```c
struct ext4_super_block {
/*00*/	__le32	s_inodes_count;
	__le32	s_blocks_count_lo;
	__le32	s_r_blocks_count_lo;	/* reserved for root */
	__le32	s_free_blocks_count_lo;
/*10*/	__le32	s_free_inodes_count;
	__le32	s_first_data_block;
	__le32	s_log_block_size;	/* 1024 << this */
	__le32	s_log_cluster_size;
/*20*/	__le32	s_blocks_per_group;
	__le32	s_clusters_per_group;
	__le32	s_inodes_per_group;
	__le32	s_mtime;
/*30*/	__le32	s_wtime;
	__le16	s_mnt_count;
	__le16	s_max_mnt_count;
	__le16	s_magic;		/* 0xEF53 */
	__le16	s_state;
	__le16	s_errors;		/* CONTINUE / RO / PANIC */
	__le16	s_minor_rev_level;
...
/*5C*/	__le32	s_feature_compat;	/* Ch. 56 T.3(d) */
/*60*/	__le32	s_feature_incompat;
/*64*/	__le32	s_feature_ro_compat;
/*68*/	__u8	s_uuid[16];
/*78*/	char	s_volume_name[16];
/*88*/	char	s_last_mounted[64];
...
	__le32	s_hash_seed[4];		/* T.4: per-fs htree hash seed */
	__u8	s_def_hash_version;
...
	__le32	s_blocks_count_hi;	/* 64bit feature */
	__le32	s_free_blocks_count_hi;
	__le16	s_min_extra_isize;
	__le16	s_want_extra_isize;
...
	__le32	s_checksum;		/* T.8 */
};
```

The `_lo`/`_hi` split is §T.1 in miniature: 64-bit support added by appending high halves rather than widening the original fields, so an old reader that ignores the `64bit` flag still reads a correct low 32 bits for a small filesystem.

`s_state`, `s_lastcheck`, `s_mnt_count`, `s_max_mnt_count` exist for the "fsck every N mounts" behaviour that everyone disables. `s_errors` controls what happens on detected corruption — `remount-ro` is the sane production setting and `panic` is correct for HA clusters that want fast failover.

### 1.3 The inode

```c
struct ext4_inode {
	__le16	i_mode;
	__le16	i_uid;
	__le32	i_size_lo;
	__le32	i_atime;
	__le32	i_ctime;
	__le32	i_mtime;
	__le32	i_dtime;		/* deletion time; 0 if live */
	__le16	i_gid;
	__le16	i_links_count;
	__le32	i_blocks_lo;
	__le32	i_flags;
	...
	__le32	i_block[EXT4_N_BLOCKS];	/* 60 bytes: indirect OR extent tree */
	__le32	i_generation;		/* Ch. 56 T.8 */
	__le32	i_file_acl_lo;		/* xattr block */
	__le32	i_size_high;
	...
	__le16	i_extra_isize;		/* T.7 */
	__le16	i_checksum_hi;
	__le32	i_ctime_extra;		/* nanoseconds + epoch bits */
	__le32	i_mtime_extra;
	__le32	i_atime_extra;
	__le32	i_crtime;		/* creation time */
	__le32	i_crtime_extra;
	__le32	i_version_hi;
	__le32	i_projid;
};
```

The timestamp encoding is worth understanding because it is how ext4 escaped 2038:

```c
#define EXT4_EPOCH_BITS 2
#define EXT4_EPOCH_MASK ((1 << EXT4_EPOCH_BITS) - 1)
#define EXT4_NSEC_MASK  (~0UL << EXT4_EPOCH_BITS)

/* The low 2 bits of *_extra are epoch bits; the rest is nanoseconds. */
static inline void ext4_decode_extra_time(struct timespec64 *time, __le32 extra)
{
	if (unlikely(extra & cpu_to_le32(EXT4_EPOCH_MASK)))
		time->tv_sec += (u64)(le32_to_cpu(extra) & EXT4_EPOCH_MASK) << 32;
	time->tv_nsec = (le32_to_cpu(extra) & EXT4_NSEC_MASK) >> EXT4_EPOCH_BITS;
}
```

Two bits extend the 32-bit seconds field to 34 bits, reaching year 2446 — and the remaining 30 bits hold nanoseconds. Packing two unrelated quantities into one field is ugly, and it is what compatibility demanded. **All of this requires a 256-byte inode.** Filesystems formatted with 128-byte inodes will break in 2038 and cannot be fixed in place.

### 1.4 `ext4_map_blocks`: the central function

Everything — buffered read, buffered write, direct I/O, writeback, fallocate — goes through one function:

```c
int ext4_map_blocks(handle_t *handle, struct inode *inode,
		    struct ext4_map_blocks *map, int flags);

struct ext4_map_blocks {
	ext4_fsblk_t m_pblk;      /* OUT: physical block */
	ext4_lblk_t m_lblk;       /* IN:  logical block */
	unsigned int m_len;       /* IN: wanted, OUT: got */
	unsigned int m_flags;     /* MAPPED / NEW / UNWRITTEN / BOUNDARY */
};
```

with flags:

```
EXT4_GET_BLOCKS_CREATE             allocate if absent
EXT4_GET_BLOCKS_UNWRIT_EXT         create as unwritten (fallocate)
EXT4_GET_BLOCKS_CONVERT            convert unwritten -> written
EXT4_GET_BLOCKS_DELALLOC_RESERVE   reserve without allocating
EXT4_GET_BLOCKS_ZERO               zero the blocks
EXT4_GET_BLOCKS_IO_SUBMIT          called from the I/O path
```

The flow:

```
ext4_map_blocks(map, flags)
 ├─ ext4_es_lookup_extent()             /* in-memory status tree: fast path */
 │    └─ HIT -> return
 ├─ (extent inode)  ext4_ext_map_blocks()
 │    ├─ ext4_find_extent()             /* walk the B+tree */
 │    ├─ found & written   -> return it
 │    ├─ found & unwritten -> convert if writing (T.3(b))
 │    └─ hole + CREATE     -> ext4_mb_new_blocks()  /* mballoc, T.5 */
 ├─ (indirect inode) ext4_ind_map_blocks()
 └─ ext4_es_insert_extent()             /* populate the status cache */
```

The **extent status tree** (`fs/ext4/extents_status.c`) is a red-black tree in memory caching the on-disk extent tree, including *holes* and *delalloc* ranges. It exists because walking the on-disk B+tree requires reading blocks and taking `i_data_sem`; the status tree answers most queries without either. It is a cache over a cache — and it has its own shrinker, because on a system with many large fragmented files it can consume real memory.

### 1.5 htree lookup

```c
static struct buffer_head *ext4_dx_find_entry(struct inode *dir,
					      struct ext4_filename *fname,
					      struct ext4_dir_entry_2 **res_dir)
{
	struct dx_frame frames[EXT4_HTREE_LEVEL], *frame;
	struct buffer_head *bh;
	ext4_lblk_t block;
	int retval;

	frame = dx_probe(fname, dir, NULL, frames);   /* descend the index */
	if (IS_ERR(frame))
		return (struct buffer_head *)frame;

	do {
		block = dx_get_block(frame->at);
		bh = ext4_read_dirblock(dir, block, DIRENT_HTREE);
		if (IS_ERR(bh))
			goto errout;

		retval = search_dirblock(bh, dir, fname,
					 block << EXT4_BLOCK_SIZE_BITS(dir->i_sb),
					 res_dir);
		if (retval == 1)
			goto success;
		brelse(bh);
		if (retval == -1) { bh = ERR_PTR(ERR_BAD_DX_DIR); goto errout; }

		/* T.4: the low hash bit says "collisions continue next block" */
		retval = ext4_htree_next_block(dir, fname->hinfo.hash, frame,
					       frames, NULL);
	} while (retval == 1);

	bh = NULL;
errout:
	dxtrace(printk(KERN_DEBUG "%s not found\n", fname->usr_fname->name));
success:
	dx_release(frames);
	return bh;
}
```

`ext4_htree_next_block` returning 1 is the collision continuation — that is the low-bit-as-flag mechanism of §T.4 in code.

### Lab 57.3 — htree, and the O(n²) it prevents

```sh
sudo mkfs.ext4 -q -F $DEV  && sudo mount $DEV  /mnt/idx
```

### Lab 57.4 — Delayed allocation and the 2009 incident

Reproduce the zero-length-file problem, then watch ext4 defend against it.

```c
// SPDX-License-Identifier: GPL-2.0
/* rename_nofsync.c -- the pattern that broke in 2009. */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(int argc, char **argv)
{
	char buf[4096];
	char tmp[256], final[256];
	int fd, i;

	memset(buf, 'A', sizeof(buf));
	for (i = 0; i < 100; i++) {
		snprintf(tmp,   sizeof(tmp), "%s/cfg%d.tmp", argv[1], i);
		snprintf(final, sizeof(final), "%s/cfg%d", argv[1], i);

		fd = open(tmp, O_WRONLY | O_CREAT | O_TRUNC, 0644);
		write(fd, buf, sizeof(buf));
		if (argc > 2 && !strcmp(argv[2], "-fsync"))
			fsync(fd);
		close(fd);
		rename(tmp, final);
	}
	return 0;
}
```

```sh
sudo mke2fs -n $DEV | grep -A2 'Superblock backups'   # -n: don't write!
sudo e2fsck -b 32768 -fy $DEV
sudo mount $DEV /mnt/e4 && ls /mnt/e4      # recovered
```

`mke2fs -n` printing the backup locations without writing is a genuinely well-designed feature and worth remembering.

And the gap ext4 cannot close:

```sh
# Corrupt FILE DATA, not metadata
sudo mount $DEV /mnt/e4
sudo sh -c 'echo "important data" > /mnt/e4/important'
sync
INO=$(stat -c %i /mnt/e4/important)
BLK=$(sudo debugfs -R "blocks <$INO>" $DEV | awk '{print $1}')
sudo umount /mnt/e4

sudo dd if=/dev/urandom of=$DEV bs=4096 seek=$BLK count=1 conv=notrunc
sudo e2fsck -fn $DEV                       # CLEAN. No error.
sudo mount $DEV /mnt/e4
cat /mnt/e4/important                      # garbage, silently
```

**`e2fsck` reports clean. That is §T.9's missing data checksum, demonstrated.** Compare with btrfs (Ch. 59), which returns `EIO` and logs a checksum failure.

### Lab 57.8 — Inodes, timestamps, and the 2038 problem

```sh
# Run out of inodes with free space remaining
sudo mkfs.ext4 -q -F -N 1000 $DEV
sudo mount $DEV /mnt/e4
df -h /mnt/e4; df -i /mnt/e4
sudo sh -c 'for i in $(seq 1 2000); do : > /mnt/e4/f$i; done' 2>&1 | tail -2
df -h /mnt/e4      # plenty of space
df -i /mnt/e4      # 100% inodes used
```

Inode size and 2038:

```sh
for isize in 128 256; do
  sudo umount /mnt/e4 2>/dev/null
  sudo mkfs.ext4 -q -F -I $isize $DEV
  sudo mount $DEV /mnt/e4
  sudo touch /mnt/e4/t
  echo "=== inode size $isize ==="
  sudo dumpe2fs -h $DEV 2>/dev/null | grep -i 'inode size'

  # Nanosecond timestamps?
  stat -c '%y' /mnt/e4/t

  # Birth time?
  stat -c '%w' /mnt/e4/t

  # Set a post-2038 timestamp
  sudo touch -d '2040-01-01' /mnt/e4/t 2>&1
  stat -c '%y' /mnt/e4/t

  # Inline xattrs?
  sudo setfattr -n user.test -v "$(python3 -c 'print("x"*100)')" /mnt/e4/t
  INO=$(stat -c %i /mnt/e4/t)
  sudo debugfs -R "stat <$INO>" $DEV | grep -iE 'extra_isize|File ACL'
  # File ACL: 0 means the xattr is INLINE (T.7)
done
```

With 128-byte inodes: no nanoseconds, no birth time, 2038 truncation, and every xattr costs a block.

Inline data:

```sh
sudo mkfs.ext4 -q -F -O inline_data $DEV
sudo mount $DEV /mnt/e4
echo "tiny" | sudo tee /mnt/e4/small > /dev/null
INO=$(stat -c %i /mnt/e4/small)
sudo debugfs -R "stat <$INO>" $DEV | grep -iE 'Inline|Size of|blocks'
stat -c '%s bytes, %b blocks' /mnt/e4/small    # 0 blocks!
```

### Lab 57.9 — `fast_commit`, fs-verity, and fscrypt

```sh
# fast_commit
sudo mkfs.ext4 -q -F -O fast_commit $DEV
sudo mount $DEV /mnt/e4
sudo dumpe2fs -h $DEV | grep -i fast_commit

cat > fsyncbench.c <<'EOF'
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <time.h>
#include <unistd.h>
int main(int argc, char **argv) {
	int fd = open(argv[1], O_WRONLY|O_CREAT|O_TRUNC, 0644), i;
	struct timespec a, b;
	char buf[4096] = {0};
	clock_gettime(CLOCK_MONOTONIC, &a);
	for (i = 0; i < 2000; i++) { write(fd, buf, 4096); fdatasync(fd); }
	clock_gettime(CLOCK_MONOTONIC, &b);
	printf("%.1f us/fdatasync\n",
	       ((b.tv_sec-a.tv_sec)*1e9 + (b.tv_nsec-a.tv_nsec)) / 2000 / 1000);
	return 0;
}
EOF
gcc -O2 -o fsyncbench fsyncbench.c
sudo ./fsyncbench /mnt/e4/fsb

sudo trace-cmd record -e ext4:ext4_fc_\* -- sudo ./fsyncbench /mnt/e4/fsb
sudo trace-cmd report | head -20
# ext4_fc_commit_start/stop and ext4_fc_track_* show the logical
# operations being recorded instead of full journal transactions.

# Compare without it
sudo umount /mnt/e4 && sudo mkfs.ext4 -q -F -O ^fast_commit $DEV
sudo mount $DEV /mnt/e4 && sudo ./fsyncbench /mnt/e4/fsb
```

fs-verity:

```sh
sudo mkfs.ext4 -q -F -O verity $DEV && sudo mount $DEV /mnt/e4
sudo apt install -y fsverity
sudo cp /bin/ls /mnt/e4/prog
sudo fsverity enable /mnt/e4/prog
sudo fsverity measure /mnt/e4/prog        # the Merkle root

sudo sh -c 'echo x >> /mnt/e4/prog'       # EPERM: immutable once enabled
# Corrupt a block on the device and read it back:
#   -> EIO on the affected page only, detected by the Merkle tree.
```

fscrypt:

```sh
sudo tune2fs -O encrypt $DEV
sudo mount $DEV /mnt/e4
sudo mkdir /mnt/e4/enc
KEY=$(head -c 64 /dev/urandom | xxd -p | tr -d '\n')
# Use `fscryptctl` or `fscrypt` to add the key and set the policy.
```

## 4. Further reading

**Kernel documentation**

- `Documentation/filesystems/ext4/` ★★★ — **the single best on-disk format documentation in the kernel.** Read `globals.rst` (superblock, group descriptors, bitmaps), `dynamic.rst` (inodes, extents, directories, xattrs), `journal.rst`, `special_inodes.rst`, and `about.rst`. Genuinely excellent; treat it as the primary reference.
- `Documentation/filesystems/ext4/ondisk/` — the structure-by-structure tables.
- `Documentation/admin-guide/ext4.rst` ★★★ — every mount option with its real meaning.
- `Documentation/filesystems/fsverity.rst`, `fscrypt.rst`
- `man 8 mke2fs`, `man 5 mke2fs.conf`, `man 8 tune2fs`, `man 8 e2fsck`, `man 8 debugfs`, `man 8 dumpe2fs` ★★★

**Papers and primary sources**

- Mathur, Cao, Bhattacharya, Dilger, Tomas, Vivier, "The new ext4 filesystem: current status and future plans," Ottawa Linux Symposium 2007 ★★★ — the design paper. Read it.
- Cao, Bhattacharya, Ts'o, "Ext4: The Next Generation of Ext2/3 Filesystem," USENIX LSF 2007.
- Card, Ts'o, Tweedie, "Design and Implementation of the Second Extended Filesystem," 1994 — the foundation.
- Tweedie, "Journaling the Linux ext2fs Filesystem," LinuxExpo 1998 — ext3's journal (Ch. 61).

- Phillips, "A Directory Index for Ext2," ALS 2001 ★★★ — htree's design paper. §T.4 in the author's words, including the compatibility trick.
- Pillai et al., "All File Systems Are Not Created Equal: On the Complexity of Crafting Crash-Consistent Applications," OSDI 2014 ★★★ — empirically catalogues what each filesystem actually guarantees. **Essential reading for anyone writing code that calls `fsync`.**
- Bairavasundaram et al., "An Analysis of Data Corruption in the Storage Stack," FAST 2008 — why §T.9's missing data checksums matter, with field data.

- "The 2038 problem" coverage, including ext4's timestamp encoding

**Source reading order**

7. `fs/ext4/inode.c`: the delalloc write path (`ext4_da_write_begin`, `ext4_writepages`).
8. `fs/ext4/fast_commit.c` — after Ch. 61.
