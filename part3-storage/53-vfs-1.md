# Chapter 53 — VFS I: superblock, inode, dentry, file, and mount

> **Goal:** Understand the Virtual File System as the kernel's most successful abstraction — an interface that unified sixty filesystems behind one syscall API — and understand it *structurally*: why there are exactly five core objects and not three or eight, why the inode/dentry split is not redundancy, why `struct file` exists separately from both, how the mount tree became a per-namespace graph with propagation semantics, and where the reference-counting rules that keep it all alive live. By the end you can name the owner and lifetime of every object in a path lookup, explain what happens to each when a filesystem is unmounted under load, and read any filesystem's `super_operations` and know what it must do.

---

## Theory & First Principles

### T.0 — Start here: `cat` works on everything

```bash
cat /etc/hostname          # ext4 on an SSD
cat /proc/cpuinfo          # generated on the fly; no storage at all
cat /sys/class/net/eth0/mtu # a kernel variable
cat /mnt/nfs/file          # a machine on the other side of the world
cat /mnt/fuse/file         # a userspace program pretending to be a filesystem
cat /dev/urandom | head -c 8   # a driver (Ch. 29)
```

**One program. Six radically different implementations. Zero special cases in `cat`.** `cat`
is 200 lines and contains no knowledge of ext4, NFS, procfs, or FUSE.

That is the VFS, and the shape is Ch. 00 §T.3b's hourglass:

```
       cat  cp  grep  python  nginx  postgres  ...          (thousands)
                         |
            open read write mmap stat ...                   (~20 syscalls)
                         |
       +-----------------v------------------+
       |  struct file_operations            |   <- THE WAIST
       |  struct inode_operations           |      ~40 function pointers
       |  struct address_space_operations   |
       +-----------------^------------------+
                         |
   ext4  xfs  btrfs  nfs  fuse  proc  sys  tmpfs  ...       (60+)
```

**Without the waist you would need `cat_ext4`, `cat_nfs`, `cat_btrfs`** — or, more
realistically, `cat` would contain a switch statement over every filesystem, and adding a
filesystem would mean patching every program. With it: *m + n* instead of *m × n*.

**Now the question that makes this a design chapter rather than a plumbing one:** what
exactly should the waist contain? Too narrow and filesystems cannot express what they do;
too wide and every filesystem must implement everything.

The VFS's answer is **four objects**, and the split between them is the actual content:

| Object | Represents | Lifetime | Why it is separate |
|---|---|---|---|
| `superblock` | a mounted filesystem | the mount | per-filesystem state and operations |
| `inode` | **a file** — its data and metadata | the file | a file exists independently of its names |
| `dentry` | **a name** in a directory | cached, reclaimable | **one file can have many names** |
| `file` | **an open file description** | an `open()` | position and flags are per-open, not per-file |

**The inode/dentry split is the one to understand**, because it is forced by a POSIX feature
that looks trivial:

```bash
touch a && ln a b        # a HARD link: two names, ONE file
stat -c '%i %n' a b      # same inode number
rm a                     # the file is NOT deleted -- b still names it
```

If a file *were* its name, hard links would be impossible. So the file (inode) and the name
(dentry) must be separate objects, and the inode carries a link count that reaches zero only
when the last name is gone. **One POSIX feature dictates the core object model of the entire
filesystem layer** — and it is also why you cannot hard-link a directory (the name graph must
stay a tree, or `rm -r` and reference counting both break).

Similarly, `struct file` is separate from `struct inode` because two processes opening the
same file need independent read positions — and because `dup()` gives you two descriptors
sharing *one* position. Three levels of indirection, each forced by an observable behaviour.

**And the dentry cache is the performance story.** Path resolution is arguably the hottest
path in the kernel:

```
  open("/usr/lib/x86_64-linux-gnu/libc.so.6")
    -> resolve "usr", then "lib", then "x86_64-linux-gnu", then "libc.so.6"
    -> 4 lookups, each of which COULD be a disk read
```

Every process start does dozens of these. The dcache makes them memory lookups, and — since
Linux 2.6 — does them **locklessly** via RCU (Ch. 15), because a shared lock on the root
directory would serialize the entire machine. Ch. 54 §T.1 is that story.

```bash
cat /proc/slabinfo | grep -E 'dentry|inode_cache'
sudo /usr/share/bcc/tools/dcstat 1     # dcache hit rate, live
ls -l /proc/self/fd/                   # your open file descriptions
stat -c '%i %h %n' /etc/hostname       # inode, link count, name
```

### T.1 The problem: N filesystems, M syscalls, and one kernel

In 1985 Sun needed NFS to work with the existing UNIX system calls without rewriting every application. Kleiman's "Vnodes: An Architecture for Multiple File System Types in Sun UNIX" (USENIX Summer 1986) is the paper that solved it, and Linux's VFS is a direct descendant.

The problem statement:

> Given N filesystem implementations with genuinely different on-disk structures, naming rules, and capabilities, and M system calls that applications already use, provide one dispatch layer such that adding a filesystem requires no change to any syscall and no change to any application.

The naive answer — a switch statement on filesystem type inside each syscall — fails on every axis: it is O(N×M) code, it requires modifying the syscall layer to add a filesystem, and it cannot support loadable modules.

The VFS answer is **polymorphism via operation tables** (Ch. 08 §T.4): each object carries a pointer to a struct of function pointers, and the generic code calls through it. `vfs_read(file)` becomes `file->f_op->read_iter(...)`, and ext4, NFS, and FUSE each supply their own.

That much is obvious. The non-obvious and much more consequential design decisions are:

1. **Which objects exist** (§T.2) — this determines what can be cached, shared, and locked independently.
2. **Which operations are generic and which are per-filesystem** — this determines how much a new filesystem must implement.
3. **Who owns the page cache** — Linux puts it in the VFS (Ch. 52), not in the filesystem, which is why `generic_file_read_iter()` works for everything.

The third decision is the one that most distinguishes Linux's VFS from the original vnode design, and it is why a minimal Linux filesystem is ~500 lines rather than ~5,000.

### T.2 Why exactly five objects

The VFS has five core object types. Each exists because it has a **distinct lifetime and a distinct sharing pattern**, and merging any two would force one of them to be duplicated or over-shared.

| Object | Represents | One per | Lifetime tied to |
|---|---|---|---|
| `super_block` | a mounted filesystem instance | mounted device/instance | the mount(s) referencing it |
| `inode` | a file (metadata + identity) | file, per superblock | links on disk + references in memory |
| `dentry` | a *name* linking a directory to an inode | (parent, name) pair | cache pressure; purely an optimisation |
| `file` | an *open* of a file | `open()` call | the fd(s) referring to it |
| `vfsmount`/`mount` | an *attachment* of a superblock into a tree | `mount()` call | the namespace holding it |

The three splits that people question, with the answers:

**(a) Why is `dentry` separate from `inode`?** Because of hard links: one inode has many names. `/a/foo` and `/b/bar` can be the same file. If name and inode were one object, either you duplicate the inode (and lose the identity that `st_ino` and locking depend on) or you store a list of names in the inode (and path lookup becomes a search). Separating them makes the name→inode mapping a cacheable, independently-reclaimable edge in a graph — which is exactly what path lookup needs (Ch. 54).

It also means the dentry cache can hold **negative entries**: "`/usr/lib/libfoo.so` does not exist" is itself worth caching, and there is no inode to attach that fact to. Negative dentries are a large fraction of the dcache on a real system and they save an enormous number of disk lookups (every `open()` failure in a search path).

**(b) Why is `file` separate from `inode`?** Because two processes can open the same file with different positions, different flags, and different credentials. `f_pos` is per-open, not per-file. `dup()` shares a `struct file` (hence a shared position); two `open()`s do not. `fork()` shares the fd table entries, hence the same `struct file`. Those three behaviours are all observable from userspace and they require exactly this three-level structure:

```
   fd table (per process)  →  struct file (per open)  →  inode (per file)
      fd 3 ─┐
      fd 4 ─┴──────────────►  file A (pos=100) ─┐
                                                ├──► inode 42
      (other process) fd 3 ─► file B (pos=0) ───┘
```

This is the same "one object, many handles" pattern as `clk_core`/`clk` (Ch. 43 §1.2) and `gendisk`/`block_device` (Ch. 51), and for the same reason: per-consumer state.

**(c) Why is `mount` separate from `super_block`?** Because one filesystem can be mounted in several places (bind mounts), in several namespaces, with different flags (`ro` here, `rw` there) — while there is exactly one instance of its cached state. The superblock is the *filesystem*; the mount is an *edge in the namespace's tree*. Bind mounts, `MS_PRIVATE`/`MS_SHARED` propagation, and containers all depend on this split (§T.6).

### T.3 The superblock: a filesystem instance

```c
struct super_block {
	struct list_head	s_list;
	dev_t			s_dev;
	unsigned char		s_blocksize_bits;
	unsigned long		s_blocksize;
	loff_t			s_maxbytes;
	struct file_system_type	*s_type;
	const struct super_operations *s_op;
	const struct dquot_operations *dq_op;
	const struct export_operations *s_export_op;   /* NFS */
	unsigned long		s_flags;      /* SB_RDONLY, SB_NOSUID, ... */
	unsigned long		s_magic;
	struct dentry		*s_root;      /* the root dentry */
	struct rw_semaphore	s_umount;     /* THE unmount lock */
	int			s_count;
	atomic_t		s_active;
	void			*s_fs_info;   /* the filesystem's private data */
	struct block_device	*s_bdev;
	struct backing_dev_info	*s_bdi;
	struct list_head	s_inodes;     /* all inodes of this sb */
	struct list_head	s_mounts;     /* all mounts of this sb */
	const struct dentry_operations *s_d_op;
	struct shrinker		*s_shrink;    /* dcache/icache reclaim */
	struct user_namespace	*s_user_ns;   /* idmapped mounts */
	uuid_t			s_uuid;
	errseq_t		s_wb_err;
};
```

`s_op` is what a filesystem must implement:

```c
struct super_operations {
	struct inode *(*alloc_inode)(struct super_block *);
	void (*destroy_inode)(struct inode *);
	void (*free_inode)(struct inode *);            /* RCU callback */

	void (*dirty_inode)(struct inode *, int flags);
	int  (*write_inode)(struct inode *, struct writeback_control *);
	int  (*drop_inode)(struct inode *);            /* keep or evict at 0 refs? */
	void (*evict_inode)(struct inode *);           /* tear down */

	void (*put_super)(struct super_block *);
	int  (*sync_fs)(struct super_block *, int wait);
	int  (*freeze_fs)(struct super_block *);
	int  (*unfreeze_fs)(struct super_block *);
	int  (*statfs)(struct dentry *, struct kstatfs *);
	int  (*show_options)(struct seq_file *, struct dentry *);

	void (*umount_begin)(struct super_block *);    /* NFS: abort RPCs */
	long (*nr_cached_objects)(struct super_block *, struct shrink_control *);
	long (*free_cached_objects)(struct super_block *, struct shrink_control *);
};
```

Two of these deserve attention because they encode real design decisions:

`alloc_inode`/`destroy_inode` exist because filesystems need to embed `struct inode` inside a larger private structure:

```c
struct ext4_inode_info {
	__le32	i_data[15];        /* the block pointers */
	__u32	i_flags;
	ext4_lblk_t i_disksize;
	/* ... 60 more fields ... */
	struct inode vfs_inode;    /* <-- the VFS's view, embedded */
};

static inline struct ext4_inode_info *EXT4_I(struct inode *inode)
{
	return container_of(inode, struct ext4_inode_info, vfs_inode);
}
```

This is Ch. 08 §T.4's `container_of`-as-inheritance, and it is why the VFS cannot allocate inodes itself. Every filesystem in the tree uses exactly this pattern, usually with a dedicated slab cache and a `SLAB_ACCOUNT | SLAB_RECLAIM_ACCOUNT` constructor.

`drop_inode` is the policy hook for "this inode's reference count hit zero — evict it or keep it cached?" The default (`generic_drop_inode`) keeps it if `i_nlink > 0` (the file still exists on disk, so caching it is useful) and evicts it otherwise (the file was deleted; nothing to cache). `tmpfs` overrides it to always evict, because there is no backing store to re-read from.

`freeze_fs`/`unfreeze_fs` support `fsfreeze(8)` — quiescing a filesystem so a block-level snapshot is consistent. It is the VFS's only "stop the world for this filesystem" primitive and it is what LVM snapshots and cloud disk snapshots rely on.

### T.4 The inode: identity and metadata

```c
struct inode {
	umode_t			i_mode;
	kuid_t			i_uid;        /* Ch. 20: nominal typing */
	kgid_t			i_gid;
	unsigned int		i_flags;      /* S_IMMUTABLE, S_NOATIME, ... */
	const struct inode_operations *i_op;
	struct super_block	*i_sb;
	struct address_space	*i_mapping;   /* Ch. 52 */
	unsigned long		i_ino;
	union {
		const unsigned int i_nlink;   /* const! use set_nlink()/inc_nlink() */
		unsigned int __i_nlink;
	};
	dev_t			i_rdev;       /* for device inodes */
	loff_t			i_size;
	struct timespec64	__i_atime, __i_mtime, __i_ctime;
	spinlock_t		i_lock;       /* protects i_state, i_count, i_nlink */
	unsigned short		i_bytes;
	u8			i_blkbits;
	blkcnt_t		i_blocks;
	unsigned long		i_state;      /* I_NEW, I_DIRTY*, I_FREEING, ... */
	struct rw_semaphore	i_rwsem;      /* THE per-inode lock */
	struct hlist_node	i_hash;
	struct list_head	i_io_list, i_lru, i_sb_list;
	struct list_head	i_dentry;     /* all dentries pointing here */
	atomic64_t		i_version;
	atomic_t		i_count;      /* in-memory references */
	atomic_t		i_writecount;
	const struct file_operations *i_fop;
	struct address_space	i_data;       /* the actual address_space */
	void			*i_private;
	/* ... union for pipes, block devices, char devices ... */
};
```

Four things that generate real bugs if misunderstood:

**(a) `i_nlink` is declared `const`.** You cannot assign to it. Use `set_nlink()`, `inc_nlink()`, `drop_nlink()`, `clear_nlink()`. The reason is that dropping to zero has consequences (the inode becomes eligible for deletion) that the VFS must observe, so it forces every change through a function. A `const` field with mutators is an unusual but effective way to enforce an invariant in C — and it is worth remembering as a technique.

**(b) `i_count` and `i_nlink` are different reference counts.**

| Count | Counts | Zero means |
|---|---|---|
| `i_nlink` | **on-disk** directory entries | the file has no name; delete it when last closed |
| `i_count` | **in-memory** references | the inode can be freed from memory |

An open file with `nlink == 0` is the classic "deleted but still open" case: the inode stays alive (`i_count > 0`), the data stays on disk, and the space is freed only when the last `close()` drops `i_count` to zero. `lsof | grep deleted` finds these, and they are why deleting a log file does not free space while the writer is running.

**(c) `i_rwsem` is the big per-file lock**, and its rules are not obvious:

| Operation | `i_rwsem` |
|---|---|
| `read()` on a regular file | **not held** (page cache + `i_size` reads are safe without it) |
| `write()` on a regular file | held **exclusive** (for POSIX write atomicity and `i_size` updates) |
| Directory lookup | held **shared** (or not at all in RCU-walk, Ch. 54) |
| Directory modification (create/unlink/rename) | held **exclusive** on the directory |
| `O_DIRECT` reads | held **shared** |
| `truncate` | held exclusive |

The exclusive-on-write rule is why a single file is a scalability bottleneck for concurrent writers, and why XFS historically used a shared lock for non-overlapping direct writes while ext4 did not. This is a real, measurable difference on database workloads.

**(d) `i_state` is a state machine.** `I_NEW` (under construction, others must wait via `wait_on_inode()`), `I_DIRTY_SYNC`/`I_DIRTY_DATASYNC`/`I_DIRTY_PAGES` (three grades of dirty, matching `fsync` vs `fdatasync`), `I_FREEING`, `I_CLEAR`, `I_WILL_FREE`, `I_SYNC`. Lookups must not return an `I_NEW` inode to a caller before it is initialised, which is what `iget_locked()`/`unlock_new_inode()` manage.

The inode cache is a global hash keyed by `(superblock, inode number)`, and the canonical filesystem idiom is:

```c
struct inode *myfs_iget(struct super_block *sb, unsigned long ino)
{
	struct inode *inode = iget_locked(sb, ino);

	if (!inode)
		return ERR_PTR(-ENOMEM);
	if (!(inode->i_state & I_NEW))
		return inode;              /* cache hit, fully initialised */

	/* Cache miss: we own it and it is I_NEW. Read from disk. */
	if (read_metadata_from_disk(inode) < 0) {
		iget_failed(inode);
		return ERR_PTR(-EIO);
	}
	inode->i_op  = &myfs_inode_ops;
	inode->i_fop = &myfs_file_ops;
	inode->i_mapping->a_ops = &myfs_aops;

	unlock_new_inode(inode);           /* clears I_NEW, wakes waiters */
	return inode;
}
```

That function shape appears in every filesystem. Learn it once.

### T.5 The dentry: names, and the cache that makes paths fast

```c
struct dentry {
	unsigned int		d_flags;
	seqcount_spinlock_t	d_seq;       /* for RCU-walk, Ch. 54 */
	struct hlist_bl_node	d_hash;
	struct dentry		*d_parent;
	struct qstr		d_name;      /* {hash, len, name} */
	struct inode		*d_inode;    /* NULL == negative dentry */
	unsigned char		d_iname[DNAME_INLINE_LEN];  /* short names inline */
	struct lockref		d_lockref;   /* spinlock + refcount, fused */
	const struct dentry_operations *d_op;
	struct super_block	*d_sb;
	void			*d_fsdata;
	union {
		struct list_head d_lru;
		wait_queue_head_t *d_wait;
	};
	struct hlist_node	d_sib;       /* sibling list */
	struct hlist_head	d_children;
	union {
		struct hlist_node d_alias;   /* inode's alias list */
		struct rcu_head	  d_rcu;
	};
};
```

Three design points:

**(a) The dcache is a *cache*, not the source of truth.** A dentry can be evicted at any time and re-created by asking the filesystem. This is what makes it safe to have an unbounded number of them and to reclaim them under memory pressure. The exception is that a dentry with a positive refcount or dirty state is pinned.

**(b) `d_iname` inlines short names.** `DNAME_INLINE_LEN` is 32 (on 64-bit), so names up to 31 characters need no separate allocation. Most filenames are short; this avoids a second allocation and a second cache miss on the hottest lookup path.

**(c) `lockref` fuses a spinlock and a refcount into one 8-byte word** that can be manipulated with a single CAS when uncontended (`lib/lockref.c`, using `cmpxchg` on the combined word). This was a targeted fix for measured dcache lock contention — the refcount operations on `/` and other hot directories were a genuine scalability limit. It is a nice example of the Ch. 16 scalability hierarchy: when a lock is too hot, remove the lock, not just the contention.

`dentry_operations` is small, and most filesystems supply none of it:

```c
struct dentry_operations {
	int  (*d_revalidate)(struct dentry *, unsigned int);   /* NFS, FUSE */
	int  (*d_weak_revalidate)(struct dentry *, unsigned int);
	int  (*d_hash)(const struct dentry *, struct qstr *);  /* case-insensitive */
	int  (*d_compare)(const struct dentry *, unsigned int,
			  const char *, const struct qstr *);
	int  (*d_delete)(const struct dentry *);   /* never cache this */
	int  (*d_init)(struct dentry *);
	void (*d_release)(struct dentry *);
	void (*d_iput)(struct dentry *, struct inode *);
	char *(*d_dname)(struct dentry *, char *, int);   /* pipes, sockets */
	struct vfsmount *(*d_automount)(struct path *);   /* autofs */
	int  (*d_manage)(const struct path *, bool);
	struct dentry *(*d_real)(struct dentry *, enum d_real_type);  /* overlayfs */
};
```

`d_revalidate` is the network-filesystem hook: "this cached name might be stale; check with the server." Local filesystems do not need it because the kernel is the only writer. The existence of this one method is what lets NFS participate in the dcache at all, and its cost is why NFS lookups are slower than local ones even when cached.

`d_dname` is how `/proc/PID/fd/3` shows `pipe:[12345]` or `socket:[67890]` — the name is *generated*, not stored.

### T.6 The mount tree: one filesystem, many attachments

```c
struct mount {
	struct hlist_node	mnt_hash;
	struct mount		*mnt_parent;
	struct dentry		*mnt_mountpoint;
	struct vfsmount		mnt;              /* the public part */
	union { struct rcu_head mnt_rcu; struct llist_node mnt_llist; };
	struct mnt_pcp __percpu	*mnt_pcp;         /* per-cpu refcount */
	struct list_head	mnt_mounts, mnt_child;
	const char		*mnt_devname;
	struct list_head	mnt_list;
	struct list_head	mnt_expire, mnt_share, mnt_slave_list, mnt_slave;
	struct mount		*mnt_master;
	struct mnt_namespace	*mnt_ns;
	struct mountpoint	*mnt_mp;
	int			mnt_id, mnt_group_id;
	int			mnt_expiry_mark;
	struct hlist_head	mnt_pins;
	struct mnt_idmap	*mnt_idmap;       /* idmapped mounts */
};

struct vfsmount {
	struct dentry	*mnt_root;    /* root of this subtree */
	struct super_block *mnt_sb;
	int		mnt_flags;    /* MNT_NOSUID, MNT_READONLY, ... */
	struct mnt_idmap *mnt_idmap;
};
```

The important structural facts:

**(a) `mnt_root` need not be `sb->s_root`.** A **bind mount** of `/data/sub` onto `/mnt` creates a mount whose `mnt_root` is the dentry for `sub`. One superblock, two mounts, two different visible roots. This one field is what makes bind mounts possible, and bind mounts are what make containers' filesystem views possible.

**(b) Flags live on the mount, not the superblock.** `/data` mounted `rw` and bind-mounted `ro` at `/readonly-data` is two `vfsmount`s with different `mnt_flags` over one `super_block`. So `MNT_READONLY` (per-mount) and `SB_RDONLY` (per-superblock) are genuinely different things, and confusing them is a common source of "why is this still writable."

**(c) Mount propagation is a graph, not a tree.** Since 2.6.15 (Ram Pai's shared-subtree work), mounts have a *propagation type*:

| Type | Behaviour |
|---|---|
| `shared` | mount/unmount events propagate **both ways** with peers in the same peer group |
| `slave` | events propagate **in** from the master, not out |
| `private` | no propagation |
| `unbindable` | private, and cannot be bind-mounted |

This exists because of a real problem: if a container's root is a bind mount of the host's, should a USB stick mounted on the host appear inside the container? Sometimes yes (a shared media directory), usually no (isolation). Propagation types let the answer be configured per subtree.

The systemd-era default is that `/` is `shared`, which is why `mount --make-rprivate /` is the first thing every container runtime does. `findmnt -o+PROPAGATION` shows it.

**(d) Mount namespaces make the whole tree per-process.** `CLONE_NEWNS` (the first namespace Linux got, in 2.4.19) gives a process its own copy of the mount tree. `/proc/self/mountinfo` shows *your* view. This is the foundation of containers, and combined with `pivot_root()` it is how a container gets a completely different filesystem view without affecting the host.

**(e) Idmapped mounts** (5.12+) let the same superblock appear with different UID/GID mappings at different mount points, via `mnt_idmap`. This solved a long-standing container problem — sharing a filesystem between containers with different UID ranges previously required either `shiftfs`, recursive `chown`, or a userspace filesystem. The mapping is applied at the VFS layer on the path from the mount, which is why it composes with everything.

**(f) `fsopen`/`fsconfig`/`fsmount`/`move_mount`** (5.2+) replaced the single overloaded `mount()` syscall. The old API took a `void *data` blob of comma-separated options parsed by each filesystem, with no way to report *which* option failed. The new API is a state machine:

```c
	fd = fsopen("ext4", 0);
	fsconfig(fd, FSCONFIG_SET_STRING, "source", "/dev/sda1", 0);
	fsconfig(fd, FSCONFIG_SET_STRING, "errors", "remount-ro", 0);
	fsconfig(fd, FSCONFIG_CMD_CREATE, NULL, NULL, 0);   /* actually mount */
	mfd = fsmount(fd, 0, MOUNT_ATTR_NODEV);
	move_mount(mfd, "", AT_FDCWD, "/mnt", MOVE_MOUNT_F_EMPTY_PATH);
```

The wins: per-option error reporting (read from `fd`), the superblock can be created without being attached anywhere (useful for containers), and the mount can be configured before becoming visible — eliminating a race where a partially-configured mount is briefly observable. This is Ch. 24 §T.3's extensibility argument applied to one of the oldest syscalls.

### T.7 `struct file` and the open-file lifecycle

```c
struct file {
	file_ref_t		f_ref;
	spinlock_t		f_lock;
	fmode_t			f_mode;
	const struct file_operations *f_op;
	struct address_space	*f_mapping;
	void			*private_data;
	struct inode		*f_inode;
	unsigned int		f_flags;      /* O_APPEND, O_NONBLOCK, ... */
	unsigned int		f_iocb_flags;
	const struct cred	*f_cred;      /* credentials AT OPEN TIME */
	struct path		f_path;       /* {mnt, dentry} */
	loff_t			f_pos;
	struct mutex		f_pos_lock;
	/* ... f_owner, f_ra (readahead state), f_security ... */
};
```

Three facts with security consequences:

**(a) `f_cred` is captured at `open()` and never re-checked.** Permission is checked once, at open. If a process opens a file it may read, then drops privileges, it can still read through that fd. This is deliberate (it is how privilege-dropping servers work) and it is why passing file descriptors over UNIX sockets (`SCM_RIGHTS`) is a capability-passing mechanism.

**(b) `f_path` holds both the mount and the dentry.** An fd knows *which mount* it was opened through, so per-mount flags (`MNT_NOEXEC`, idmapping) apply correctly for its whole lifetime, even if the file is later renamed or the mount moved.

**(c) `f_pos_lock` serialises position updates**, but only for files where it matters. `stream_open()` (Ch. 29 §T.5) marks a file as having no meaningful position, so concurrent reads do not serialise — which is what makes `/dev/urandom` and pipes scale.

The open path (`fs/open.c`, `fs/namei.c`) is:

```
openat(dfd, path, flags, mode)
 └─ do_sys_openat2()
     ├─ build_open_flags()          /* validate flags, compute acc_mode */
     ├─ get_unused_fd_flags()       /* reserve an fd slot */
     └─ do_filp_open() → path_openat()
         ├─ path_init(); link_path_walk()      /* Ch. 54 */
         └─ open_last_lookups() + do_open()
             ├─ may_open()          /* permission, O_NOFOLLOW, sticky, ... */
             ├─ vfs_open() → do_dentry_open()
             │    ├─ f->f_op = inode->i_fop
             │    ├─ security_file_open()
             │    └─ f->f_op->open(inode, f)    /* the fs/driver hook */
             └─ fd_install(fd, file)            /* NOW visible to userspace */
```

`fd_install()` last is not an accident: until then, an error can be cleanly unwound without userspace ever seeing a partially-constructed fd.

### T.8 `inode_operations` vs `file_operations`: the split that confuses everyone

Two operation tables, and which method goes where follows one rule:

> **`inode_operations` act on the *namespace* (names and metadata). `file_operations` act on the *contents* of an open file.**

| `inode_operations` (needs a name/directory) | `file_operations` (needs an open file) |
|---|---|
| `lookup`, `create`, `link`, `unlink`, `symlink` | `read_iter`, `write_iter` |
| `mkdir`, `rmdir`, `mknod`, `rename` | `iterate_shared` (readdir) |
| `getattr`, `setattr` (stat/chmod/truncate) | `mmap`, `fsync`, `flush`, `release` |
| `permission`, `get_inode_acl` | `llseek`, `poll`, `unlocked_ioctl` |
| `listxattr`, `fileattr_get/set` | `open`, `fallocate`, `splice_read/write` |
| `get_link` (readlink), `tmpfile` | `copy_file_range`, `remap_file_range` |
| `fiemap`, `update_time`, `atomic_open` | `uring_cmd`, `get_unmapped_area` |

Two consequences:

- A **directory** has both: `i_op` with `lookup`/`create`/etc., and `i_fop` with `iterate_shared` (so you can `read()` a directory via `getdents`). A **regular file** has an `i_op` that is mostly `getattr`/`setattr` and an `i_fop` that does the real work.
- `readdir` lives in `file_operations` because it needs a position (where you are in the directory) — which is per-open state, hence on `struct file`. That is the same argument as §T.2(b).

The modern `iterate_shared` (replacing `iterate`) takes `i_rwsem` **shared**, allowing concurrent readdir on one directory. Getting there required making every filesystem's directory-reading path safe against concurrent readers, which took years — a good illustration of how a locking relaxation in a shared layer is a tree-wide project.

### T.9 What a minimal filesystem must implement

The payoff of the VFS's design is how little a new filesystem needs. For a simple read-write disk filesystem:

| Table | Mandatory members |
|---|---|
| `file_system_type` | `mount`/`init_fs_context`, `kill_sb`, `name`, `owner` |
| `super_operations` | `alloc_inode`, `free_inode`, `statfs`, and usually `write_inode`, `evict_inode` |
| `inode_operations` (dir) | `lookup`, `create`, `unlink`, `mkdir`, `rmdir`, `rename` |
| `inode_operations` (file) | usually **none** — `setattr`/`getattr` defaults suffice |
| `file_operations` (file) | `read_iter`, `write_iter`, `mmap`, `fsync` — **all generic** |
| `file_operations` (dir) | `iterate_shared` |
| `address_space_operations` | `read_folio`, `writepages`, `write_begin`, `write_end` (or use `iomap`) |

Everything with "generic" in the name is free:

```c
const struct file_operations myfs_file_ops = {
	.llseek		= generic_file_llseek,
	.read_iter	= generic_file_read_iter,
	.write_iter	= generic_file_write_iter,
	.mmap		= generic_file_mmap,
	.fsync		= generic_file_fsync,
	.splice_read	= filemap_splice_read,
	.splice_write	= iter_file_splice_write,
};
```

Those six lines give you buffered reads with readahead, buffered writes with dirty tracking and throttling, mmap with demand paging, and splice — all of Ch. 52, for free, because the page cache lives in the VFS. This is the concrete payoff of the §T.1(3) design decision, and it is why `fs/ramfs/` is 250 lines and Ch. 56 can build a real filesystem in one chapter.

### 1.2 Object lifetimes and who holds what

```
   task
     └─ files_struct (fd table)
          └─ struct file        [f_ref]
               ├─ f_path.dentry [d_lockref]
               │    ├─ d_parent (a reference)
               │    └─ d_inode  [i_count]
               │         └─ i_sb
               └─ f_path.mnt    [mnt_pcp count]
                    └─ mnt_sb   [s_active]
```

The rules:

| Reference | Taken by | Dropped by | Notes |
|---|---|---|---|
| `file->f_ref` | `open`, `dup`, `fget` | `close`, `fput` | `fput` may defer to a workqueue (see below) |
| `dentry->d_lockref.count` | `dget`, lookup | `dput` | dropping to 0 does **not** free; it goes on the LRU |
| `inode->i_count` | `igrab`, `iget` | `iput` | 0 → `drop_inode` decides evict or keep |
| `mnt` count | `mntget`, path walk | `mntput` | per-CPU for scalability |
| `sb->s_active` | each mount | `deactivate_super` | 0 → the filesystem is torn down |

**`fput()` can defer.** If the last reference is dropped in a context that cannot sleep (an interrupt, or under a lock), `fput()` queues the actual teardown to a workqueue (`delayed_fput`) or to task-work (`fput_many`/`task_work_add`). This matters because `->release()` can do I/O. The observable consequence: a file is not necessarily fully closed when `close()` returns, which occasionally surprises people testing unmount-after-close.

**Dropping a dentry refcount to zero keeps it cached.** This is the dcache's whole point — the next lookup of the same name is a hash hit. Eviction happens via the shrinker under memory pressure, or explicitly via `d_invalidate()`/`shrink_dcache_parent()`.

### 1.3 The unmount problem

`umount` must ensure nothing is using the filesystem. The machinery:

```
umount(path)
 └─ path_umount() → do_umount()
     ├─ may_umount_tree() / check for child mounts
     ├─ if (!(flags & MNT_DETACH)) check mnt refcount -> -EBUSY
     ├─ lock_mount_hash(); umount_tree(mnt, UMOUNT_PROPAGATE)
     └─ deactivate_super(sb)  when s_active hits 0
         ├─ sb->s_op->put_super()
         ├─ shrink_dcache_for_umount()    /* must find NO busy dentries */
         ├─ evict_inodes()                /* must evict ALL inodes */
         ├─ sync_filesystem()
         └─ kill_block_super() / kill_anon_super()
```

`shrink_dcache_for_umount()` will `BUG()` if a dentry is still in use at this point, because by then the unmount has committed. This is why a filesystem bug that leaks a dentry reference manifests as a panic at unmount, far from the cause — the classic "works fine until you unmount" bug.

`MNT_DETACH` (lazy umount, `umount -l`) detaches the mount from the namespace immediately and lets the superblock die when the last reference goes. It is the reason `umount -l` "works" when `umount` says `-EBUSY`, and also why it is a footgun: the filesystem is still mounted, just invisible.

`s_umount` is a rwsem held across the whole operation and taken by anything that needs the superblock to stay alive and unchanging (`sync`, `remount`, `freeze`). Lock-ordering rules around it are documented in `Documentation/filesystems/locking.rst` and are a common source of lockdep reports in new filesystems.

### 1.4 The caches and their shrinkers

```sh
slabtop -o | head -20
# dentry, inode_cache, ext4_inode_cache, filp, and the per-fs inode caches
```

Both the dcache and the icache are reclaimed by shrinkers (Ch. 23 §T.6):

- `sb->s_shrink` is a per-superblock shrinker registered with `SHRINKER_NUMA_AWARE | SHRINKER_MEMCG_AWARE`.
- It scans `s_dentry_lru` and `s_inode_lru` — **per-superblock LRUs**, not global. This means unmounting a filesystem reclaims its caches in bounded time, and a memcg's pressure reclaims its own.
- `vfs_cache_pressure` (`/proc/sys/vm/`) scales how aggressively these are reclaimed relative to the page cache. Default 100; lowering it favours keeping metadata cached.

A subtlety: evicting an inode requires evicting its dentries first (a dentry pins its inode), and evicting a dentry requires its children to be gone. So reclaim proceeds leaf-first up the tree, and a deeply-pinned path (e.g. a process's cwd) pins every ancestor.

Or do it programmatically with the new mount API of §T.6(f):

```c
// SPDX-License-Identifier: GPL-2.0
#define _GNU_SOURCE
#include <fcntl.h>
#include <linux/mount.h>
#include <stdio.h>
#include <sys/syscall.h>
#include <unistd.h>

static int sys_open_tree(int dfd, const char *path, unsigned flags)
{ return syscall(__NR_open_tree, dfd, path, flags); }
static int sys_mount_setattr(int dfd, const char *path, unsigned flags,
			     struct mount_attr *attr, size_t size)
{ return syscall(__NR_mount_setattr, dfd, path, flags, attr, size); }
static int sys_move_mount(int ffd, const char *fpath, int tfd,
			  const char *tpath, unsigned flags)
{ return syscall(__NR_move_mount, ffd, fpath, tfd, tpath, flags); }

int main(void)
{
	/* A userns whose mapping we want to apply. */
	int userns_fd = open("/proc/self/ns/user", O_RDONLY);
	struct mount_attr attr = {
		.attr_set = MOUNT_ATTR_IDMAP,
		.userns_fd = userns_fd,
	};
	int tree = sys_open_tree(AT_FDCWD, "/mnt/idmap-src",
				 OPEN_TREE_CLONE | OPEN_TREE_CLOEXEC |
				 AT_RECURSIVE);

	if (tree < 0) { perror("open_tree"); return 1; }
	if (sys_mount_setattr(tree, "", AT_EMPTY_PATH | AT_RECURSIVE,
			      &attr, sizeof(attr))) {
		perror("mount_setattr"); return 1;
	}
	if (sys_move_mount(tree, "", AT_FDCWD, "/mnt/idmap-dst",
			   MOVE_MOUNT_F_EMPTY_PATH)) {
		perror("move_mount"); return 1;
	}
	printf("idmapped mount created\n");
	return 0;
}
```

Note the shape: `open_tree(OPEN_TREE_CLONE)` creates a *detached* mount, you configure it while it is invisible, then `move_mount()` attaches it atomically. That is §T.6(f)'s race-free construction, and it is the pattern to use for anything non-trivial.

### Lab 53.5 — The new mount API, and its error reporting

```c
// SPDX-License-Identifier: GPL-2.0
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <unistd.h>
#include <linux/mount.h>

static int fsopen_(const char *fs, unsigned f)
{ return syscall(__NR_fsopen, fs, f); }
static int fsconfig_(int fd, unsigned cmd, const char *k, const void *v, int aux)
{ return syscall(__NR_fsconfig, fd, cmd, k, v, aux); }
static int fsmount_(int fd, unsigned f, unsigned ms)
{ return syscall(__NR_fsmount, fd, f, ms); }
static int move_mount_(int ffd, const char *fp, int tfd, const char *tp,
		       unsigned f)
{ return syscall(__NR_move_mount, ffd, fp, tfd, tp, f); }

static void drain_messages(int fd)
{
	char buf[4096];
	ssize_t n;

	while ((n = read(fd, buf, sizeof(buf) - 1)) > 0) {
		buf[n] = 0;
		/* 'e' = error, 'w' = warning, 'i' = info */
		printf("  fs says: %s", buf);
	}
}

int main(int argc, char **argv)
{
	int fsfd, mfd, ret;

	fsfd = fsopen_("tmpfs", FSOPEN_CLOEXEC);
	if (fsfd < 0) { perror("fsopen"); return 1; }

	fsconfig_(fsfd, FSCONFIG_SET_STRING, "size", "16M", 0);

	/* A deliberately bad option, to show per-option error reporting. */
	ret = fsconfig_(fsfd, FSCONFIG_SET_STRING, "bogus", "1", 0);
	printf("bad option -> %d (%s)\n", ret, ret ? strerror(errno) : "ok");
	drain_messages(fsfd);

	if (fsconfig_(fsfd, FSCONFIG_CMD_CREATE, NULL, NULL, 0)) {
		perror("CMD_CREATE"); drain_messages(fsfd); return 1;
	}

	mfd = fsmount_(fsfd, FSMOUNT_CLOEXEC, MOUNT_ATTR_NOSUID);
	if (mfd < 0) { perror("fsmount"); return 1; }
	close(fsfd);

	/* The superblock exists and is configured but is attached NOWHERE.
	 * We could pass mfd to another process over SCM_RIGHTS here. */
	printf("mount fd = %d (not yet visible in the tree)\n", mfd);
	sleep(2);

	if (move_mount_(mfd, "", AT_FDCWD, argv[1] ?: "/mnt",
			MOVE_MOUNT_F_EMPTY_PATH)) {
		perror("move_mount"); return 1;
	}
	printf("attached\n");
	close(mfd);
	return 0;
}
```

```sh
gcc -o newmount newmount.c && sudo ./newmount /mnt
findmnt /mnt
```

Compare with the old API's error reporting:

```sh

# "mount: /mnt: wrong fs type, bad option, bad superblock..." -- which option?
dmesg | tail -3
```

That contrast is the entire argument for the new API.

```sh
ls -l /proc/*/fd/* 2>/dev/null | grep /mnt/busy

# Case 2: an open fd
exec 9< /mnt/busy/file
sudo umount /mnt/busy            # EBUSY
exec 9<&-

# Case 3: a nested mount
sudo mkdir -p /mnt/busy/sub
sudo mount -t tmpfs tmpfs /mnt/busy/sub
sudo umount /mnt/busy            # EBUSY
sudo umount -R /mnt/busy         # recursive works

# Case 4: mount propagation keeps it alive elsewhere
sudo mount --make-shared /mnt/busy
sudo mount --bind /mnt/busy /mnt/other
sudo umount /mnt/busy            # succeeds, but /mnt/other...
findmnt | grep other

# Lazy umount and why it is a footgun
sudo umount -l /mnt/busy
findmnt | grep busy              # gone from the tree
cat /proc/self/mountinfo | grep busy
# but the superblock lives until the last reference drops
sudo lsof | grep /mnt/busy
```

Now the diagnostic checklist, which is the deliverable:

| `umount` says | Check |
|---|---|
| `target is busy` | `fuser -vm`, `lsof +D`, `/proc/*/cwd`, `/proc/*/root`, `/proc/*/fd` |
| busy but nothing found | a *kernel* reference: loop devices (`losetup -a`), swap (`swapon -s`), NFS exports, a nested mount in another namespace |
| busy in a container context | `nsenter` into every mount namespace: `for p in /proc/*/ns/mnt; do ...` |
| hangs forever | the filesystem is blocked in writeback or on a dead device; `cat /proc/*/stack`, `echo w > /proc/sysrq-trigger` |

The "another namespace" case is the one that defeats people:

```sh
# Find every namespace that has this mounted
for p in /proc/[0-9]*; do
  pid=${p#/proc/}
  if sudo grep -qs " /mnt/busy " $p/mountinfo 2>/dev/null; then
    echo "pid $pid ($(cat $p/comm)) ns=$(sudo readlink $p/ns/mnt)"
  fi
done | sort -u -k4
```

## 3. Mastery drills

1. Prove that the inode/dentry split is *necessary* for hard links by showing that any single-object design either duplicates identity or turns lookup into a search. Then explain what `d_alias` is for and what invariant it maintains.

2. `i_nlink` is `const` with mutator functions. List three other invariants in the kernel that could be enforced this way, and state the cost of the technique.

3. A file is deleted while open. Trace exactly which reference counts change at `unlink()` and at `close()`, and name the function that actually frees the disk blocks.

4. `read()` does not take `i_rwsem` but `write()` takes it exclusive. Show that this still satisfies POSIX's requirement that a write be atomic with respect to concurrent reads, and identify the mechanism (hint: it is not `i_rwsem`).

5. Negative dentries cache non-existence. Construct a workload where they are a memory-exhaustion vector, and describe what the kernel does about it. (Look for the negative-dentry-limiting discussions.)

6. `lockref` fuses a spinlock and a refcount. Write the CAS-based fast path, prove it is correct against a concurrent lock-holder, and explain when it falls back.

7. Design the propagation semantics from scratch: given the requirement "a container must see the host's `/media` mounts but the host must not see the container's," derive which of shared/slave/private each mount needs.

8. `mnt_root != sb->s_root` enables bind mounts. Show what breaks if path resolution ignores `mnt_root` when walking *up* past a bind-mounted subtree's root.

9. Compare the old `mount(2)` and the new `fsopen`/`fsconfig`/`fsmount`/`move_mount` API against Ch. 24's four extensibility mechanisms. Which does each use, and what class of future change does the new one accommodate?

10. `fput()` can defer to a workqueue. Construct a test that observes the deferral, and explain why `->release()` cannot simply be called from `close()` in all cases.

11. `shrink_dcache_for_umount()` BUGs on a busy dentry. Design an alternative that fails the unmount instead, and explain why the kernel does not do this.

12. Idmapped mounts apply a UID mapping at the VFS layer. Enumerate every place a UID appears in a path operation (permission check, `stat` output, file creation, xattrs, quota) and verify the mapping is applied consistently at each.

13. A filesystem developer reports "unmount panics but only after heavy use." Give the ordered diagnostic procedure and the three most likely root causes, with the specific kernel debug option that would catch each.

## 4. Further reading

**Kernel documentation**

- `Documentation/filesystems/vfs.rst` ★★★ — **the** reference. Every structure and every method documented, with the contract for each. Read it in full once, then keep it open.
- `Documentation/filesystems/locking.rst` ★★★ — which lock is held when each method is called, and what each method may block on. Indispensable when writing a filesystem; the source of most "my filesystem deadlocks" answers.
- `Documentation/filesystems/path-lookup.rst` ★★★ — Neil Brown's exposition; mostly Ch. 54's material but the dentry model is here.
- `Documentation/filesystems/mount_api.rst` ★★★ — §T.6(f) in detail, with the rationale.
- `Documentation/filesystems/idmappings.rst` ★★★ — Christian Brauner's very thorough treatment; the clearest writing on UID mapping anywhere.
- `Documentation/filesystems/sharedsubtree.rst` ★★★ — Ram Pai's original document on mount propagation. Short, with worked examples.
- `Documentation/filesystems/porting.rst` — the running log of VFS API changes; effectively a changelog of every sharp edge.
- `Documentation/filesystems/api-summary.rst`, `directory-locking.rst` ★★ — the latter is essential for `rename` correctness.

**Papers**

- S. R. Kleiman, "Vnodes: An Architecture for Multiple File System Types in Sun UNIX," USENIX Summer 1986 ★★★ — the origin of §T.1. Short and still worth reading.
- R. Sandberg et al., "Design and Implementation of the Sun Network Filesystem," USENIX Summer 1985 — the motivating use case.
- M. K. McKusick et al., "A Fast File System for UNIX," 1984 — for the on-disk side the VFS abstracts.
- J. Corbet's documentation of the dcache and the RCU-walk work, plus P. E. McKenney's RCU papers (Ch. 15) — the dcache is one of RCU's flagship users.
- A. Bhattacharya et al. and the various "scalable VFS" papers — background for the lockref and per-superblock-LRU work.

**LWN — the history of every decision in this chapter**

- "The new mount API" series (2018–2019) ★★★ — Al Viro and David Howells on §T.6(f)
- "Mount namespaces and shared subtrees" / "Shared subtrees" (2016, Michael Kerrisk) ★★★
- "ID-mapped mounts" (2021) and Christian Brauner's write-ups ★★★
- "RCU-walk: faster pathname lookup in Linux" (Neil Brown, 2015, two parts) ★★★
- "Dcache scalability and lockref" (2013)
- "Negative dentries, 20 years later" (2020) — drill 5's material
- "The trouble with `iterate_shared`" and the readdir-locking series
- "Filesystem mounts and the container problem" — recurring LSFMM coverage
- Michael Kerrisk's "Mount namespaces and shared subtrees" series is the best tutorial on propagation that exists.

**Books**

- Bovet & Cesati, *Understanding the Linux Kernel*, Ch. 12 — the classic long-form VFS chapter. Dated in API, correct in structure.
- Robert Love, *Linux Kernel Development*, Ch. 13 — concise and accurate; the best short introduction.
- Michael Kerrisk, *The Linux Programming Interface*, Ch. 14, 18, 37 — the userspace view, which is what the VFS must implement. The namespaces material in the online supplements is essential for §T.6.
- W. R. Stevens & S. Rago, *Advanced Programming in the UNIX Environment*, Ch. 3–4 — the POSIX semantics the VFS is obliged to provide.

**Source reading order**

1. `fs/ramfs/` — all of it, ~250 lines. It is a complete filesystem and it shows exactly which methods are mandatory.
2. `fs/libfs.c` — the helpers ramfs uses; `simple_lookup`, `simple_statfs`, `simple_dir_operations`.
3. `include/linux/fs.h` — the five structures and all op tables. Read the comments.
4. `fs/inode.c` — `iget_locked()`, `iput()`, `evict()`, `new_inode()`.
5. `fs/dcache.c` — `d_alloc()`, `d_lookup()`, `dput()`, `d_instantiate()`. Dense but central.
6. `fs/super.c` — `sget()`, `deactivate_locked_super()`, and the `kill_*_super` family.
7. `fs/namespace.c` — `do_mount()`, `attach_recursive_mnt()`, and `fs/pnode.c` for propagation. Hard; read with `sharedsubtree.rst`.
8. Then a real filesystem's `super.c` — `fs/ext2/super.c` is the most readable.

**Tools**

- `findmnt` ★★★ (`-o+PROPAGATION,ID,PARENT`, `--tree`, `--poll`)
- `/proc/self/mountinfo` ★★★ — the authoritative view, with propagation
- `lsof` (`+D`, `+L1`, `-p`), `fuser -vm`
- `stat`, `/proc/PID/fdinfo/N`, `/proc/PID/{cwd,root,exe}`
- `unshare -m`, `nsenter -t PID -m`, `mount --make-{shared,slave,private,unbindable}`
- `slabtop -o`, `/proc/slabinfo`, `/proc/sys/fs/{dentry-state,inode-state,file-nr}`
- `bpftrace` on `d_alloc`, `__dentry_kill`, `iget_locked`, `iput`, `do_mount`
- `mount-idmapped` (from `samples/vfs/` or util-linux 2.40+)
